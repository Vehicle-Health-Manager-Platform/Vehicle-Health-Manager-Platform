# A5 商家派工与技师接单：下一阶段计划

日期：2026-10-08。状态：规划草案，供下一阶段规格细化；本次仅整理计划，不实现 A5。

基线：[Spec](../../SPEC.md) F14/F16/F18、[履约状态规格](../specs/2026-10-07-fulfillment-state-design.md)、[A4 接口](../../api/PICKUP_OWNER_DECISION.md)。A5 的前置是 A4 阶段验证并上传 GitHub。

## 目标与建议路径

让商家把已由车主确认的本店订单派给本店有效技师，技师能在本人工作台查看、接单，并由服务端推进订单状态。建议先做“一单一位技师、首次派工与接单”，便于明确归属与并发约束；多技师协作、改派和拒单各有额外状态及补偿规则，需要后续独立明确。

接车检查完成、车主已确认、订单无争议是确定的派工前置。草案接口契约还写有“防护齐全才派工”，而 Spec 要求“防护未上传不能报工”，A6 才交付防护；实施前必须统一这处规则，不能通过写入虚假防护证据绕过。

## 分步交付

| 顺序 | 工作 | 完成条件 |
| --- | --- | --- |
| A5.1 | 细化派工与接单规格 | 明确派工主体、可选技师、接单与施工开始的关系、改派/拒单范围、防护的校验时点 |
| A5.2 | 数据与后端 | 核对已有 `technician_assignment` 表；新增迁移、候选技师读取、本店派工、本人接单及工单查询，复用行锁、幂等与审计 |
| A5.3 | 商家与技师界面 | 商家订单可选本店技师并查看派工状态；技师工作台展示本人派工，详情可接单，具备加载、空态、失败及会话失效处理 |
| A5.4 | 权限与竞争验证 | 他店/停用/非技师账号拒绝；未确认和争议订单不可派工；非本人不可接单；重复与并发操作只产生一次有效变更，失败完整回滚 |
| A5.5 | 本机联调与 GitHub 收口 | 用合成订单和隔离商家/技师身份完成派工→本人查询→接单；中文契约、迁移、验收记录和进度文档齐全；推送阶段分支、建立 PR、全部 CI 通过 |

## 必须在规格中明确的业务选择

- 推荐首次仅支持一单一位技师；已接单之后的改派与撤回是否后置。
- 推荐派工写 `assigned_at`，技师接单时检查车主确认与派工归属并开始施工；应据此决定通用商家 `START_SERVICE` 是否退役，避免两个入口独立推进状态。
- 技师候选必须属于本店且有效；是否要求已绑定微信，以及无候选技师时的界面提示。
- 防护应在派工、施工开始还是报工处阻断，须统一 Spec、旧草案与 A6 交付时点。

上述内容是待细化的推荐值，不作为已确认业务规则。
