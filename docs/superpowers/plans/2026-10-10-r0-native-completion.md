# R0.1b2c 微信原生核销、本人评价与施工档案计划

日期：2026-10-10。依赖 #72 / `e589f4e`，沿用已确认微信原生验收设计及下一步安排；只实施微信小程序与必要后端。

## 取舍

采用前序原生施工脚本连续生成独立来源，随后验证原生核销、评价和档案。相比 SQL 伪造完成状态，多运行一次原生施工能保留真实付款/接车/签字来源；相比读取旧订单，独立新订单不会覆盖前次评价与审计。后端现有规则和界面保持当前业务规格，运行中发现具体缺陷再修正。

## 实施步骤与判定

1. 导出既有施工执行和清理函数，独立 CLI 行为保留。前序 21 项来源验收单列，不混入本阶段原生通过总数。校验隔离镜像/JAR、支付 profile 与归档消费者已启用；不开启正式环境功能。
2. 未核销订单的车主评价页面须显示资格阻断；核销码从车主原生订单详情读取，核对测试付款标注。其他门店核销页不得取得本店内容。
3. 商家输入错误六位码得到实际接口错误且无核销记录；正确码取消不写入；确认后真实核销完成，记录唯一且保留 test_mode。
4. 从车主订单详情进入本人评价，真实评分/文字及真实上传的合成测试图片；取消不写入，确认后唯一评价并只读；重进页面保留记录和测试标注。
5. 等待既有可靠归档任务完成，不伪造任务状态；原生档案页选车、显示实际工时/测试来源/配件和施工图片入口，再点击来源订单展示完成状态与评价入口。
6. 新增合成另一车主，检查其评价、档案及档案证据访问拒绝；商家不能代替本人评价。本人档案证据授权只证明接口权限，不冒充证书下图片视觉渲染通过。
7. 成功与失败均恢复实际安装的 mock、撤销本次会话、清空身份及源 PNG；保留隔离订单/审计。仅关闭本项目并移除临时 URL 校验例外，不触及其他项目/容器。

## 验收边界和收口

原生业务请求、上传、扫描、核销、评价和数据库不 mock；系统选择器与确认结果继续官方 mock 辅助，复选框/画布沿用官方事件。不计真机、人工签名或真实扣款通过。后台归档及权限 HTTP 检查与原生页面结果分类记录。
