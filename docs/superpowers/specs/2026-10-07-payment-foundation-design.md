# 支付基础与隔离测试渠道设计

日期：2026-10-07。基线：main `1c54f61`（PR #24）；主分支 CI `37562181961` 六项成功。用户已确认先交付支付基础与隔离测试渠道，并确认下述设计范围。状态：用户已确认书面规格，已按中文计划实施，最终验收见执行记录。

## 目标与方案选择

完成 F07/F08 的支付基础子集：本人支付发起与查询、支付状态与订单状态联动、通知校验/去重、异常持久化和订单到期竞态。复用预约订单、支付表和成功审计，保持金额快照与预约容量一致。

比较两种交付路径：先建立支付基础和隔离测试渠道，可在本机验证全部状态、并发与回滚；直接接正式微信支付，可验证真实扣款，但依赖商户号、AppID 绑定、私有证书及渠道通知入口。用户选择前者；公网、云托管和真机继续后置。

本步不实现正式微信扣款、退款执行、优惠券、佣金、对账任务、商家接车/派工或核销。异常记录供后续退款核对，不声称已经退款。完整交易闭环和 S2 验收仍未完成。

## 模块与环境边界

- 支付应用服务负责身份、金额、记录、锁和审计；渠道接口负责渠道识别、准备支付参数及验证通知，不能由前端选择签名算法或提交支付结果。
- 正式 `WECHAT` 渠道本步未配置，发起返回 503 和明确不可支付提示；不生成伪造的微信支付参数，不调用 `uni.requestPayment`。
- `LOCAL_TEST` 为独立测试渠道，默认关闭。仅在 `local-payment-test` Spring profile 与 `PAYMENT_LOCAL_TEST_ENABLED=true` 同时成立、且独立签名密钥至少32字节时允许注册；启用配置不完整时启动失败。生产 profile 与该测试 profile 并用时启动失败。
- 测试密钥仅由私有环境提供，不复用 JWT/微信密钥，不进入客户端。部署模板默认关闭测试渠道。本机测试必须指向固定隔离数据库/回环后端，由验收工具核对环境；不对日常已有订单批量生成测试成功。
- 所有测试支付记录保留 `channel=LOCAL_TEST`；订单响应中的支付摘要保留渠道和 `test_mode=true`。页面醒目标注“测试支付，未真实扣款”，后续处理也不能把该记录作为真实收款凭据。
- 隔离测试通知由专用本机验收工具或集成测试发送；普通小程序没有模拟成功/失败按钮，亦不能取得签名密钥。

## 支付发起与重试

- 有效 OWNER 仅对本人未删除订单发起支付。正文严格为 `order_id, channel`，不接受金额、用户/商家 ID、支付状态或渠道流水号。
- 订单须为 `PENDING_PAYMENT`、服务器时间严格早于订单到期时间，且预约尚未开始；支付金额来自订单 `pay_amount` 的精确两位小数字符串，币种固定 `CNY`。改价不改变订单金额。
- 本步支付开始时间和到期时间沿用订单，不延长占位。订单取消或自动到期时，同事务将其进行中的本地支付记录关闭；这只表示本地不可继续支付，不声称已经关闭外部渠道交易。
- 同一订单最多一笔 `CREATED/PENDING` 支付，按订单锁串行查找。不同幂等键的同时发起返回同一有效支付记录，不再创建第二笔；同键异文拒绝。
- 请求使用24小时 UUID 幂等。缓存重放仍复核当前身份与归属，返回原始创建收据；当前状态由查询获取，重放不会重新开单或恢复已关闭支付。
- `FAILED` 后可在原订单仍有效时用新键发起新支付；旧失败支付保留。请求重放原键返回旧记录，前端需明确点击重新发起才换键；网络错误重试继续用原键。
- 本机测试渠道的准备结果只含支付编号/测试标识/到期时间，不含外部副作用。禁止在 `WriteIntegrityService` 的事务回调内调用外部网络；正式渠道未来另行设计稳定请求号、渠道查询及恢复流程。

## 通知契约与校验

只有 `POST /api/payments/callback/LOCAL_TEST` 为本步独立实现的无 Bearer 通知入口，且关闭测试渠道时返回404。安全配置不放开其他未实现渠道的任意路径。

测试通知 JSON 严格包含：`event_id`（UUID）、`payment_id`（正安全整数）、`channel_payment_no`（1–128位字母数字及下划线/连字符）、`status`（`SUCCEEDED` 或 `FAILED`）、`amount`（正数两位小数）、`currency`（`CNY`）、`order_no`、`occurred_at`（带时区 ISO 8601）。请求体最多16 KiB，不接受额外字段或重复 JSON 键。

签名头为 `X-Test-Timestamp`（Unix秒）、`X-Test-Nonce`（UUID）、`X-Test-Signature`（64位十六进制）。HMAC-SHA256 输入为 `timestamp + "\n" + nonce + "\n" + 原始UTF-8正文 + "\n"`，固定时间比较，发送时间与服务器时间相差不超过300秒。签名规则仅属于本机测试渠道，不代表微信验签算法。重投时可重新签名，业务事件 ID 不变。

验证顺序：开关/长度/格式、签名和时间窗，再读取支付并校验渠道、订单号、金额和币种。`occurred_at` 不得晚于服务器时间加300秒；过期与取消判断使用服务器事务内当前时间，不以通知中的发生时间恢复预约名额。

事件摘要按已验证的业务字段规范化计算，不含签名头/nonce。相同渠道与事件 ID、相同摘要返回已提交确认；同 ID 不同摘要返回409。非法签名、金额、币种、订单或渠道不匹配返回4xx，不更新订单/支付，不输出原文、密钥或 SQL。

## 状态转换与异常

| 当前记录/订单 | 合法通知或操作 | 处理结果 |
| --- | --- | --- |
| 进行中支付、有效待支付订单 | SUCCEEDED | 支付 `SUCCEEDED`，记录流水号与成功时间；订单 `PAID`，支付/事件/成功审计同事务；名额继续占用 |
| 进行中支付、有效待支付订单 | FAILED | 支付 `FAILED`，订单仍待支付且原到期时间不变，允许新键发起新支付 |
| 待支付订单 | 本人取消或服务器到期 | 订单关闭与名额释放沿用预约模块，进行中支付同事务 `CLOSED`；失败/已成功历史记录不覆盖 |
| 已取消/过期订单，或已 CLOSED/FAILED 的旧支付 | SUCCEEDED | 记录渠道确已报告成功的事实，支付转 `SUCCEEDED`，并写待核对异常；不把订单转 PAID、不恢复容量 |
| 订单已由另一支付成功 | 其他支付 SUCCEEDED | 保存第二笔成功事实和重复收款待核对异常，不重复改变订单/占位 |
| 已成功支付 | FAILED 或新的重复成功事件 | 不回退成功；分别记录忽略结果或重复结果，不重复订单成功审计 |
| 已关闭/失败支付 | FAILED | 保留原状态，记录已处理结果，不覆盖历史成功或关闭原因 |

支付 `SUCCEEDED` 表示收到并验证渠道成功事实，是否可用于履约以订单 `PAID` 且无该支付异常为准。本机测试结果始终显示测试标识。成功通知事务内若订单已经到期但后台未处理，先按现有过期规则关闭、释放、系统审计，再保存迟到付款异常。

每笔成功支付最多一条待核对异常（唯一支付 ID）；原因包括订单取消、订单到期、旧失败支付成功、重复收款，状态为 `OPEN`。保留支付/订单 ID、渠道与金额、原因、创建时间；不保存通知原文/签名，也不添加自动退款或人为“处理完成”接口。

多个异常条件同时满足时原因优先级为：另一笔支付已成功、订单取消、订单到期、旧失败支付成功。异常原因首次记录后不由重复通知覆盖；关闭原因未知的历史订单使用 `ORDER_CLOSED`，不推测主动取消或到期。

成功后不再执行未支付取消，前端关闭该操作，服务端拒绝；以后由退款契约处理。PAID 仍占时段容量，未支付到期任务不关闭 PAID。

## 事务、锁与事件去重

- 客户端支付发起沿用身份与 UUID 幂等，授权阶段锁本人会话/用户，然后按“商家 → 时段 → 订单 → 支付 → 幂等记录”顺序锁业务资源；缓存命中也核对归属。
- 通知不锁用户身份，按“商家 → 时段 → 订单 → 支付 → 事件记录”顺序，读取使用当前锁定结果；与创建预约、取消、自动过期一致，不引入倒置锁顺序。
- 容量始终通过预约模块计算实际未关闭订单；支付成功只改变状态，不另加一次名额。过期后成功不得重新取得已经释放的名额。
- 事件插入、支付/订单更新、异常和系统审计同一独立事务提交，成功提交后才确认渠道。审计或数据库失败返回503并全部回滚，可由同事件重试。
- 不依赖进程内去重锁；渠道+事件唯一键、渠道+流水号唯一键及业务行锁在多实例下保证一次处理。不同支付重复流水号冲突时整事务拒绝，不能串到其他订单。
- 回调审计 actor 为 `system/0`，区分支付成功、失败与异常；重复事件直接复用确认，不再写转换审计。无效通知使用不含凭据的结构化错误日志，本步不假称已接告警平台。

## 数据迁移与 API

新增可重复执行 V008，不改历史迁移：`payment` 补稳定支付编号、币种、到期、失败/关闭时间与订单索引；新增 `payment_event`（渠道+事件 ID 唯一、支付 ID、规范化摘要、处理结果）和 `payment_exception`（支付 ID 唯一、订单/支付/渠道/金额/原因/状态）。新表均包含公共时间及软删除字段。预计总表数由46变48，门禁核对实际结果。历史缺少编号/到期的支付不自动伪造有效请求或渠道成功。

| 方法与路径 | 身份 | 本步契约 |
| --- | --- | --- |
| POST `/api/payments/create` | OWNER | UUID键；`order_id, channel`；返回支付 ID/编号、状态、金额/币种、渠道、测试标识、到期和渠道参数 |
| GET `/api/payments/{id}` | OWNER本人 | 查询本人的支付状态与异常标识，不暴露原始渠道流水/签名；本店商家支付查询后续接入 |
| POST `/api/payments/callback/LOCAL_TEST` | 测试渠道签名 | 按上述严格通知契约；提交成功200固定确认，非法4xx，暂不可用503 |
| GET `/api/order/list`、`/api/order/{id}` | OWNER本人 | 扩展 PAID 过滤及支付摘要，保留待支付/已关闭兼容与测试标识 |

客户端继续统一 JSON/no-store 响应；400参数/键冲突、401会话、403角色、404本人资源/关闭测试渠道、409状态/事件内容冲突、503数据库/未配置正式渠道。回调成功为固定 `{ "code": "SUCCESS" }`，独立于前端业务响应包装；验证失败不返回成功确认。

## 小程序体验

- 订单详情保留待支付、到期、刷新与取消；新增正式微信支付按钮，明确尚未配置，调用服务端也不可支付。不得用本地跳转或客户端回调写 PAID。
- 展示最近支付状态及“支付失败可重新发起”信息；查询失败/身份切换/隐藏页面清空或隔离迟到响应，网络不确定状态原键重试。测试支付在隔离验收中由工具发起，页面只展示其状态与明确测试标识。
- 已支付页面显示“已支付待接车”，不提供未支付取消；本步接车未交付，提示后续服务流程尚未接入。测试支付同时显示“未真实扣款，不可作为收款凭据”。
- 订单列表支持待支付/已支付/已关闭，状态与金额来自服务端；不在客户端推断支付成功或自动生成核销码。
