# R9 A4d-2h3 车主评价与独立公开授权验收设计

## 目标

把"车主提交评价 → 本人查看 → 独立授权公开星级 → 独立投稿公开文本 → 运营审核 → 公开展示 → 摘要第三方用途授权"这条件链路，用真实 HTTP 跑通并把失败留在报告里。覆盖 14 个已存在接口，**不新增业务能力**：本阶段补的是可复现验收与门禁，以及过程中暴露的校验缺陷。

## 为什么不合并成一个"公开评价"开关

产品上这是四个彼此独立的授权，代码里也必须是四条独立记录：

| 授权 | 存储 | 撤回影响 |
| --- | --- | --- |
| 私人评价 | `order_review` + `order_review_file` | 不可撤回、不可修改 |
| 公开星级 | `review_publication(review_id, consented, version)` | 只影响星级聚合，评价本身保留 |
| 公开文本 | `public_review_text` + `public_review_text_moderation` | 清空当前文字与公开编号，保留审核履历 |
| 摘要第三方用途 | `review_summary_consent(review_id, consented, version, text_version)` | 只撤销"发送给第三方模型"这一用途 |

合并会带来两个真实的越权面：撤销星级授权却继续公开展示文字，或改稿后仍按旧文本版本向第三方发送。所以验收必须逐条验证"撤销 A 不影响 B、但 B 自己的版本必须重新核对"。

## 夹具口径

身份、订单、支付、核销、图片全部是 SQL 合成夹具；**评价与四种授权全部走 HTTP**。这是与之前阶段一致的口径，也决定了本轮能证明什么、不能证明什么。

合成订单矩阵（`order` 表 6 行）：

| 订单 | 状态 | 渠道 | 核销 | 争议 | 用来验证 |
| --- | --- | --- | --- | --- | --- |
| 1 | COMPLETED | LOCAL_TEST | 有 | 无 | 可评价，但星级不能公开（TEST_ORDER） |
| 2 | COMPLETED | WECHAT | 有 | 无 | 完整公开链路（星级/文本/摘要） |
| 3 | PENDING_PAYMENT | 无 | 无 | 无 | ORDER_NOT_COMPLETED |
| 4 | COMPLETED | WECHAT | 无 | 无 | REDEMPTION_UNVERIFIED |
| 5 | COMPLETED（他人） | WECHAT | 有 | 无 | 越权 404 |
| 6 | COMPLETED | WECHAT | 有 | OPEN | OPEN_DISPUTE |

公开星级与公开文本的"实时可信来源"判定要求唯一 WECHAT 成功付款、金额与币种匹配、渠道单号与付款时间齐全、唯一 PAID 事件且哈希完整、无支付异常/开放争议/退款。订单 1 用 LOCAL_TEST，就是为了证明**本地测试订单不会被迁进正式公开样本**。

图片 `file_object` 另插 3 行：两张属于车主 1（CLEAN，PNG/JPEG），一张属于车主 2，用来验证"他人文件 422"。所有图片只是元数据，不涉及真实存储。

## 两个开关

`REVIEW_TEXT_PUBLICATION_ENABLED` 与 `REVIEW_SUMMARY_ENABLED` 生产默认都是 `false`，代码里以 `${...:false}` 回退值写死。隔离运行器显式传 `true`，否则"投稿/审核/生成"三条链路根本不会被触发，等于没验收。

因此本阶段的状态是：**隔离环境显式开启、生产默认未改**。单测会同时断言两件事——隔离环境变量为 `true`，而 `ReservationConfiguration` 里两个 `@Value` 的回退值仍是 `false`。这样"默认关闭"有代码级证据，不靠嘴说。

## 版本链与"重复决策"为什么是 200 不是 409

三个公开相关记录各有一条单调递增的 `version`，验收必须按真实递增顺序断言，否则用例自己就会写错：

| 记录 | 首次写入 | 审核通过 | 撤回 |
| --- | --- | --- | --- |
| `review_publication` | 1 | — | 2 |
| `public_review_text` | 1（PENDING） | 2（APPROVED） | 3（WITHDRAWN） |

`review_summary_consent` 另记 `text_version`：授权时的文本版本被冻结在授权行里，`effective` 要求它仍等于当前文本版本。所以文本撤回后 `page/public_text` 立刻不再公开，而授权行仍是 `consented=1, text_version=2`——这正好证明"撤回文本不等于撤回第三方用途授权"，也让"改稿后旧授权自动失效"可被验证。

审核接口的 `expected_version` 是"我要审的那一版"。同一决定重复提交时（`current == requested + 1` 且目标状态已达成、审核履历里的决定与理由一致），后端按幂等重放处理：返回 200 与当前状态，**不二次写 `public_review_text_moderation`，也不二次写 `audit_log`**。断言 409 是错的——那等于要求"重复点一次审核就报错"，反而会诱导前端做无意义的版本补偿。真正的 409 只出现在两种情形：`expected_version` 既不是当前版也不是当前版的前一版，或者同一版本想改成相反的决定。用例对三种情形分别断言 200 重放、版本冲突 409、决定冲突 409，落库再核 `PUBLIC_REVIEW_TEXT_MODERATE` 的审计只有一行。

## 判定

- 每个操作必须覆盖 `normal / boundary / error / unauthorized` 四类，缺一类审计直接拒绝。这是既有门禁的硬要求，也是防止"只测好路径"的机制。
- 断言必须来自实际响应：审计逐项核对方法、路径、真实 query、真实身份令牌、状态码、幂等键是否就是计划的那一个，任一被替换即失败。
- 落库核对：评价不可变、`test_mode` 跟随核销、图片位置顺序、公开记录撤回后 `consented=0` 且版本递增、文本撤回后正文与公开编号被清空但审核履历保留、摘要授权绑定 `text_version`。
- 脱敏按 `TEXT_REDACTION_V1`：手机号、邮箱、VIN、车牌、7 位以上数字都要变成 `[已隐藏]`；投稿必须与预览结果逐字一致，否则 422。

## 不覆盖

正式微信身份与资金、真实对象存储签名、真实第三方模型调用、评分聚合的统计显著性、真机与 UI 展示效果。公开文本的脱敏是规则式替换，会有漏匹配，不能当作合规认证；本轮只验证"规则被真实执行且不可绕过"。

## 未做的判断

不把"通过 14 接口验收"当作"评价功能整体完成"：AI 摘要质量、公开页面的信息层级、审核工作量评估都不在本阶段。也不因为验收通过就调整生产开关。
