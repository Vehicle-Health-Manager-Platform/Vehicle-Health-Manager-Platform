# S1 本人车辆档案拍照录入

日期：2026-10-05。基线为已合并 PR #12–#16 的 `main`。用户选择先交付拍照录入，并确认新增档案录入方式 `input_type=1`；手动方式继续为 `3`。

## 目标与范围

车主在档案 Tab 选中本人车辆后，可从“拍照录入”入口打开现有记录表单的拍照模式。用户点击“拍照并上传”唤起相机，至少一张图片上传成功后，填写档案类型、发生日期、标题及可选里程和备注，再保存记录。最多关联五张图片，可预览、移除、使用原图和同一上传幂等键重试。保存后在档案 Tab 及首页摘要中看见该记录和正确记录数。

比较三种做法：① 复用现有表单并增加拍照模式，字段与图片状态只有一套；② 建独立拍照页面，会重复上传、预览、保存逻辑；③ 把相机图片仍保存为手动方式，无法准确追踪来源。采用①，同时准确保存拍照来源。相机取消保留表单；相机权限、上传或保存失败给出可重试提示。用户可返回档案 Tab。既有手动录入保持可无图片保存。

本步不做 OCR、图片内容识别、语音转写、类型专属字段、编辑删除或订单自动归档。照片本身不推断档案类型、日期、里程或标题；用户确认这些字段。生产私有存储和真实微信相机仍需环境联调。

## 接口与持久化

- `POST /api/archive/add` 在严格字段白名单中加入可选整数 `input_type`。省略时取 `3`，仅接受 `1` 或 `3`；`1` 必须有 1–5 个不重复图片 ID，`3` 允许 0–5 个；`2` 拒绝。规范化后的 `input_type` 参与 24 小时幂等正文比较，避免相同幂等键在不同方式间复用。
- 保存前沿用有效 OWNER 会话、本人未删除车辆和每张图片的本人、未删除、`CLEAN` 检查；在原事务中写 `vehicle_archive.input_type`、图片关联、幂等结果与成功审计。成功审计增加录入方式，不写图片 URL、标题或备注。无需新迁移。
- `GET /api/archive/list` 对本人车辆同时分页返回 `input_type IN (1,3)` 的记录；每条带 `input_type`，总数与列表使用同一过滤口径，仍按发生日期及 ID 倒序。首页使用该接口第一页与 `total`，自然计入拍照记录。语音方式 `2` 留待后续契约。
- 图片继续通过现有私有上传与短时访问接口；上传成功只得到文件 ID，保存时才建立档案关系。签名 URL 不存入档案或本地持久状态。现有 HTTP 状态与安全错误文案沿用。

## 小程序流程与状态

档案 Tab 在当前车辆操作区提供“手动录入”和“拍照录入”。两个入口进入 `/pages/archive/record-add`，仅拍照入口传 `mode=photo`；服务端从令牌验证车辆归属，路由参数不构成授权。拍照模式的选择器只请求相机；手动模式继续允许相册或相机。用户明确点击相机按钮才触发系统权限请求，不在页面加载时自动打开。

拍照表单展示已上传张数、每张预览和移除；未上传图片时禁用保存，提交前客户端也复核 `input_type=1` 和附件数量。无论录入方式，上传失败保留原本地图片与上传幂等键，修改档案正文后档案幂等键重新生成；未改正文重试沿用原键。账户变化、页面隐藏或卸载时清除私有表单并丢弃迟到结果。列表展示“拍照录入”或“手动录入”来源，首页最近记录也显示来源。

## 验证与交付

后端测试覆盖默认手动、拍照无图/有图、非法方式、同键不同方式、本人和跨车主图片、事务审计及混合方式分页总数。小程序测试覆盖相机专用 `sourceType`、取消/权限失败、拍照必填图片、手动无图兼容、列表来源和首页摘要。运行小程序与 H5 构建及仓库 CI；有可用浏览器或微信测试环境时再做页面交互和真机相机联调，并如实记录未执行项。更新接口契约、OpenAPI、进度与执行记录，以独立 PR 提交，不把此步视为完整 F03/M1 验收。
