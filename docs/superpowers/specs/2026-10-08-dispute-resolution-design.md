# 争议处理、车主复核与恢复条件规格

> 更新日期：2026-10-08｜状态：**规则已确认，可实现**。前置：[接车与履约状态规格](2026-10-07-fulfillment-state-design.md) §2/§9
> 的 `DISPUTED → 前一状态`（D5）、[A4 车主确认与异议](../../api/PICKUP_OWNER_DECISION.md)、
> [A5 派工与技师接单](2026-10-08-a5-dispatch-design.md)。
>
> **要解决的问题**：A4 只交付"第一次决定"。车主提出异议后订单置 `DISPUTED`，此后商家侧没有任何
> 可执行动作（`allowed_actions=[]`），车主侧也没有任何入口，订单永久停在争议里。规格 §2 早写明
> `DISPUTED → 前一状态` 由"争议解决"写入，但该流程一直不存在。本规格补齐它。

## 1. 争议生命周期

一条争议从产生到结束只有两种终局：**解决并恢复**（车主复核接受商家处理），或**保持未解决**
（车主不接受，可继续沟通）。争议全过程必须完整留痕：原因、商家的处理、车主的最终决定。

```
RECEIVED --车主异议--> DISPUTED
                          |
             商家提交处理记录（可多次，至少一条）
                          |
             车主复核 <---+-----------------> 不接受：争议保持 OPEN，订单仍 DISPUTED，可继续处理
                 |
              接受
                 v
        订单恢复争议前状态（RECEIVED）+ 接车单 owner_confirm=3
                 |
                 v
        派工 → 技师本人接单 → 施工（A5 链路恢复可用）
```

**恢复条件（缺一不可）**：

| 编号 | 条件 | 不满足时 |
| --- | --- | --- |
| R1 | 订单当前为 `DISPUTED`，且存在状态为 `OPEN` 的争议单 | `40905` |
| R2 | 争议单记录的"争议前状态"是 `PAID`/`RECEIVED`/`IN_SERVICE`/`PENDING_VERIFY` 之一 | `40905`（历史异常数据 fail-closed） |
| R3 | 对应接车单存在、未删除，且 `owner_confirm=2`（曾是异议） | `40905` |
| R4 | 商家已提交至少一条处理记录 | `43008` |
| R5 | 由**车主本人**发起复核，且请求来自本人有效会话 | `401`/`403`/`404` |

**恢复动作的完整效果（同一事务）**：

1. `order_dispute.status` 由 `OPEN` 改为 `RESOLVED`，写 `resolved_at`、`resolved_by`；
2. `order.status` 由 `DISPUTED` 回到争议单记录的 `from_status`；
3. `pickup_check.owner_confirm` 由 `2` 改为 `3`，并写 `order.owner_confirmed_at`；
4. 写一条 `order_status_transition`（`DISPUTED → from_status`，`action='ORDER_DISPUTE_RESOLVE'`，`actor_type='user'`）；
5. 写一条 `order_dispute_record`（`ACCEPT`）；
6. 写 `audit_log`；幂等响应与以上全部同事务提交，任一步失败整体回滚。

## 2. 已确认的业务规则

| 编号 | 问题 | 结论 | 理由 |
| --- | --- | --- | --- |
| E1 | 恢复的目标状态怎么定？ | **回到该争议发生前的状态**，取自争议单自身记录的 `from_status`，不硬编码 `RECEIVED` | 与规格 §2「`DISPUTED →` 前一状态」一致；也为将来从 `PAID`/`IN_SERVICE` 直接提异议留出空间，无需改规则 |
| E2 | 谁能宣布争议解决？ | **车主本人**。商家只能提交处理记录，**不能自行恢复订单** | 异议由车主提出，单方面由商家解除争议等于把阻断权交给被投诉方 |
| E3 | 接受处理是否等于确认接车单？ | **是**。`owner_confirm` 置 3，写 `owner_confirmed_at`，派工前置随之成立 | 车主接受处理即同意按现有接车记录继续履约；若仍不接受接车记录，应继续"不接受"而不是接受 |
| E4 | 处理记录可以提交几次？ | **可以多次**，每次追加一条时间线记录；至少一条才能复核 | 真实沟通需要多轮；只保留最后一条会丢掉过程，"完整留痕"要求全过程可见 |
| E5 | 车主不接受会怎样？ | 争议保持 `OPEN`，订单仍 `DISPUTED`，新增一条 `REJECT` 记录；商家可继续提交处理记录 | 不引入超时自动处理，也不允许无限次单方面恢复 |
| E6 | 一个订单能有几条争议？ | **只允许一条**（`order_dispute.order_id` 唯一）。争议解决后接车单 `owner_confirm=3`，A4 的决定入口要求 `owner_confirm=0`，因此**不能再提第二次异议** | 一条争议一个完整闭环，避免历史叠加导致投影含义不清；再次异议若确有必要，另行设计 |
| E7 | 订单关闭能否绕过争议？ | **不能**。`DISPUTED` 不在 `CLOSED` 的来源集合里，商家通用动作矩阵不含争议解决；三端都没有"关闭争议订单"的入口 | 退款与取消属 A7 范围，此处保持 fail-closed |

**假设（可调）**：E3 之外，`ACCEPT` 允许附 0–500 字说明，`REJECT` 必须附 1–500 字原因，
`HANDLE` 必须附 1–500 字处理说明。长度上限与 A4 的异议原因一致（500 字），不新造阈值。

## 3. 权限与可见性

| 角色 | 可做的 | 不可做的 |
| --- | --- | --- |
| 车主（OWNER） | 本人在本订单上复核（接受/不接受）；读取本人接车单（含争议时间线） | 提交商家处理记录；复核他人订单；替商家写处理说明 |
| 商家（MERCHANT） | 本店订单提交处理记录；读取本店接车单与争议时间线 | 宣布争议解决、恢复订单、改车主决定 |
| 技师（TECHNICIAN） | 无争议接口权限 | 读写任何争议记录 |

**不得泄露**：争议时间线只投影 `action`、`note`、`created_at`，**不投影任何 `actor_id`**
（车主 ID、商家员工 ID 都不出现在响应里）。这与 A5 的最小投影规则一致：投影过滤之外，
`idempotency_record.response_body` 与 `audit_log.before_state/after_state` 同样不得落隐私字段。

## 4. 状态与错误码

新增两个业务前置码，沿用 `4300x` 段位（`43001`–`43006` 已被 A3/A5/A6 占用，见
[订单履约契约](../../api/ORDER_FULFILLMENT.md)）：

| 码 | 含义 | 出现场景 |
| --- | --- | --- |
| `43007` | 订单存在未解决的争议，不能派工或接单 | 派工/接单前置校验看到 `DISPUTED` |
| `43008` | 商家尚未提交处理记录，暂不能复核 | 车主在接受复核时，争议下没有任何 `HANDLE` 记录 |

`43007` 是对既有行为的**收敛而非放宽**：`DISPUTED` 订单此前也派不了工（返回通用 `40905`），
现在改为明确的业务码，让商家/技师界面能直接提示"请先在接车单处理争议"。`OrderStatus` 的
商家动作矩阵不变——`DISPUTED` 仍不出现任何商家 `allowed_actions`。

其余错误码沿用现有约定：参数无效 `40001`，会话失效 `401`，角色不符 `403`，非本人/非本店/不存在 `404`，
状态冲突 `40905`，数据库不可用 `50300`。所有争议响应继续带 `Cache-Control: no-store`。

## 5. 数据模型

`order_dispute`（每订单最多一行，争议单本身）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `order_id` | BIGINT | 唯一键 `uk_order`；一单一争议 |
| `merchant_id` | BIGINT | 冗余本店归属，供商家侧筛选，派工前已校验一致 |
| `pickup_check_id` | BIGINT | 产生该争议的接车单 |
| `reason` | VARCHAR(500) | 车主异议原因，从接车单复制，争议期间不可修改 |
| `from_status` | VARCHAR(32) | 争议发生前的订单状态，恢复时写回 |
| `status` | VARCHAR(16) | `OPEN` / `RESOLVED` |
| `opened_by` / `opened_at` | BIGINT / DATETIME | 提出异议的车主与时间 |
| `resolved_at` / `resolved_by` | DATETIME / BIGINT | 车主接受复核的时间与本人 |
| `created_at` / `updated_at` / `is_deleted` | 同既有表约定 | |

`order_dispute_record`（时间线，只追加）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `dispute_id` / `order_id` | BIGINT | 归属，`KEY idx_dispute (dispute_id,id)` |
| `action` | VARCHAR(24) | `HANDLE`（商家处理）、`ACCEPT`（车主接受）、`REJECT`（车主不接受） |
| `actor_type` | VARCHAR(16) | `user` / `staff_account` |
| `actor_id` | BIGINT | 仅落库留痕，**不投影给任何角色** |
| `note` | VARCHAR(500) | 处理说明/复核说明 |
| `created_at` | DATETIME | |

迁移 `V013__dispute_resolution.sql` 可重复执行：表数由 50 增至 52；`pickup_check.owner_confirm`
的列注释同步为 `0待1确认2异议3争议已解决`（仅注释，不改类型）。历史争议数据不自动回填——
A4 之前提出异议的订单没有争议单，恢复入口对它们保持关闭（fail-closed），由人工处理。

## 6. 接口

| 方法 | 路径 | 角色 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/api/merchant/orders/{id}/dispute/handle` | MERCHANT | 提交一条处理记录（1–500 字），可多次 |
| `POST` | `/api/check/pickup/dispute/review` | OWNER | 复核：`ACCEPT` 恢复订单，`REJECT` 保持争议 |
| `GET` | `/api/check/pickup/{order}`（既有） | OWNER/MERCHANT | 投影新增 `dispute` 字段，含时间线与 `can_review` |

不新增读接口：争议时间线嵌在已有的接车单投影里，商家与车主读同一份，避免两套视图漂移。
请求/响应、错误码与幂等语义见[争议处理契约](../../api/DISPUTE_RESOLUTION.md)。

商家侧订单详情（`/api/merchant/orders/{id}`）保持只读投影不变，`DISPUTED` 的
`allowed_actions` 仍为 `[]`；页面改从接车单进入处理入口，理由与处理记录只在接车单页可见。

## 7. 锁顺序与并发

复用既有顺序，不引入新锁层级：**商家 → 时段 → 订单 → 接车单 → 争议单 → 争议记录 → 幂等记录**
（派工链路里的派工行被跳过，不构成与 `商家 → 时段 → 订单 → 派工 → 接车单` 的反向等待）。
车主复核为 **车主 → 商家 → 时段 → 订单 → 接车单 → 争议单**，与 A4 的车主决定同序。

并发语义：

- 两名商家员工同时提交处理记录：两次都成功，时间线两条（追加语义，不是竞争）；
- 车主复核与商家提交处理记录并发：按行锁串行，复核要么看到处理记录（成功），要么返回 `43008`；
- 同一车主两次并发复核：最多一次恢复订单，第二次读到 `status=RESOLVED` 返回 `40905`；
- 复核与派工并发（异键）：派工只能看到 `DISPUTED`（返回 `43007`）或恢复后的 `RECEIVED`（成功），
  不存在"半个争议"的中间态。
