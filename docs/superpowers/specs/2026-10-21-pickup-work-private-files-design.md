# 接车与施工私有附件访问验收设计

本阶段补齐四个遗留的私有附件访问接口：接车检查图片（`GET /api/check/pickup/{order}/files/{file}/access`）、商家施工证据（`GET /api/merchant/orders/{id}/work/files/{file}/access`）、技师施工证据（`GET /api/tech/orders/{id}/work/files/{file}/access`）与车主施工证据（`GET /api/order/{id}/work/files/{file}/access`）。四者都是"先鉴权、再签短时 URL"的读接口，风险集中在归属判定与签名本身，而不是状态机。

## 方案选择

Newman 业务套件（A4d-2 起的默认做法）只起后端与 MySQL，无法在真实对象存储里放文件，也无法真正下载签名 URL 并验证字节一致、篡改拒绝和自然过期。因此沿用 A4d-2e2b（私有上传）与 A4d-2g3（辅助材料）已验证的形态：Java 旅程测试起真实 MySQL/MinIO/ClamAV，Python 执行器只做证据审计与归档。与"只加 SQL 夹具 + 断言签名参数"相比，本方案能证明 URL 真的能取回原始字节，且撤掉签名后真的取不到。

## 被测流程

身份、订单与支付为 SQL 合成夹具（`PAID`、预约码、`appointment_snapshot`），其余全部走真实 HTTP：

1. 商家上传 7 张接车图片 → 提交接车单（预约码校验、7 槽位、里程不回退）→ 车主确认。
2. 商家派工 → 技师接单（`RECEIVED → IN_SERVICE`）。
3. 商家上传防护照并提交防护；技师上传施工过程/故障件/完工三张照片与 PNG 签字图，报工后签字（`IN_SERVICE → PENDING_VERIFY`）。
4. 第二张订单同样真实上传 7 张接车图片并提交接车单，用于跨订单隔离。

共 19 个 CLEAN 文件、14 条接车附件关联、5 条施工证据关联（PROTECTION/PROCESS/FAULT/FINISH/SIGNATURE）。

## 权限矩阵

| 接口 | 允许 | 拒绝（业务语义） |
| --- | --- | --- |
| 接车附件 | 本店 MERCHANT/STAFF；本单车主 | 技师 403（门店账号专属）；他人车主 404；他店 404；未关联到本单的文件 404 |
| 商家施工证据 | 本店 MERCHANT/STAFF | 他人车主 403（角色不符）；他店 404；接车图片走本接口 404 |
| 技师施工证据 | 本单已接单技师 | 车主 403；同店未派工技师 404；接车图片 404 |
| 车主施工证据 | 本单车主 | 商家 403；他人车主 404；他人订单的接车图片 404 |

约定沿用既有实现：越权读一律 `404`（不暴露资源是否存在），角色不符一律 `403`；四个接口都只认路径参数，未知/重复 query 返回 `40001`。

## 签名与租期

签名 URL 由 `PrivateFileAccessService` 在鉴权后签发，TTL 取隔离配置 5 秒，响应体只有 `url` 与 `expires_at`，并带 `Cache-Control: no-store`。验收要求：下载回传字节与上传字节逐字节一致、`Content-Type` 为 `image/png`；去掉 query 后对象存储返回 403；把 `X-Amz-Signature` 改一个字符返回 403；等待 6 秒后同一 URL 返回 403。车主侧访问在签名前后各复核一次归属（存储 I/O 期间撤权/删除不得返回旧授权），该逻辑沿用既有实现，本阶段只补执行证据。

## 生产代码变更

只修一处真实缺口：接车附件访问此前忽略未知/重复 query（同一路由对不同调用方语义不一致），现与其余三个接口一致，拒绝任何 query 参数。其余四个服务与控制器逻辑零改动。

## 边界

- 扫描引擎是真实 ClamAV，但签名库为合成；生产鲜度策略未改。
- 身份、订单、支付、派工时间为合成夹具；正式微信身份、真实资金未覆盖。
- 5 秒签名只测一次自然过期；未做长时间压测、真机或外部云存储验收。
- 全 API 验收仍为 false，本阶段只把四项接口从"无四类证据"变为"有可复现四类证据"。
