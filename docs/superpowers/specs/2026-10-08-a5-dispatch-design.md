# A5 商家派工与技师接单规格

日期：2026-10-08。状态：A5.1 规格交付；A5.2 后端已编码并进入验证，A5.3–A5.5 尚未验收；证据见[A5.2 执行记录](../../progress/A5_2_DISPATCH_BACKEND_EXECUTION.md)。用户在收到 A5 建议计划后要求“开始下一步”，本规格将建议路径细化为实施基线；新增工程选择标为【假设】，允许后续调整，不记录为用户逐项确认。

依据：[Spec](../../SPEC.md) F14/F15/F16/F18、[履约规则](2026-10-07-fulfillment-state-design.md)、[A4 契约](../../api/PICKUP_OWNER_DECISION.md)。本规格新增的 API 契约见[派工与技师接口](../../api/TECHNICIAN_DISPATCH.md)，编码步骤见[中文实施计划](../plans/2026-10-08-a5-dispatch.md)。

## 1. 目标与范围

商家将本店已接车、车主已确认的订单派给本店有效技师；技师在本人工作台查看工单并接单，服务端随后推进施工状态。按 A5.1 规格、A5.2 后端、A5.3 界面、A5.4 验证、A5.5 联调与收口交付，每个已完成子阶段同步文档并上传 GitHub。

| 方案 | 取舍 | 本阶段选择 |
| --- | --- | --- |
| 一单一位技师，首次派工与接单 | 复用已有订单唯一派工约束，归属和竞争行为清晰 | 采用 |
| 接单前允许改派/撤回 | 需要版本、撤回记录和旧技师操作失效规则 | 后续独立规格 |
| 多技师协作、拒单和再分配 | 需要主技师、协作权限及补偿流程 | 后续独立规格 |

本阶段包含候选技师、首次派工、商家派工结果、本人工作台/工单详情、本人接单。防护上传、施工报工、质检、完工核销归 A6/A7；争议处理与恢复另行设计。首版通过页面进入与手动刷新获取结果，不承诺短信、微信订阅消息或实时推送。

## 2. 业务规则与决策

| 编号 | 规则 | 依据与属性 |
| --- | --- | --- |
| A5-D1 | 一单仅一位技师；不提供改派、撤回、拒单 | 【假设】沿用建议路径与 `technician_assignment.uk_order` |
| A5-D2 | 仅有效本店商家可派工；不得传入商家 ID 决定归属 | Spec F16 与既有商家会话规则 |
| A5-D3 | 派工前订单必须为 `RECEIVED`，接车证据完成、车主确认且无争议 | Spec F14/F16、A4 已实现决定 |
| A5-D4 | 候选技师是本店 `TECHNICIAN/ACTIVE` 员工且在当前服务端 AppID 下有有效微信绑定；不要求当前在线 | 【假设】确保派出后具备登录接单能力；不把会话是否在线作为人员资格 |
| A5-D5 | `technician_id` 指 `staff_account.id`，不是微信绑定 ID；解绑不会改写派工历史 | 与既有 JWT subject/staffId 一致 |
| A5-D6 | 派工只写派工记录和 `order.assigned_at`，订单保持 `RECEIVED`；本人接单将派工置 `ACCEPTED` 并把订单置 `IN_SERVICE` | 【假设】让接单成为明确的施工开始动作 |
| A5-D7 | A5 接入时停止对外开放商家通用 `START_SERVICE`，仅技师接单可推进此迁移 | A5-D6 的必要约束，避免绕过本人接单 |
| A5-D8 | 防护照片不阻断派工/接单；A6 报工时缺防护返回 `43002` | Spec F15/§2.2；修正 S0 接口草案的冲突描述 |
| A5-D9 | 接单时重新校验接车、车主确认、无争议、本人派工和身份有效 | Spec F14/F18；派工时的检查不能代替写入时复核 |
| A5-D10 | 人员停用/解绑后既有派工保留，工单不可由其他技师接单；恢复资格后本人可继续。人员变更不自动开通改派 | 【假设】安全保留责任归属，后续人员处置单独设计 |

“接车证据完成”要求 `check_in_completed_at` 非空并有本订单、本店、未删除的接车单；“车主已确认”同时要求 `owner_confirmed_at` 非空、该接车单 `owner_confirm=1` 且 `confirm_at` 非空。不通过伪造时间列、默认确认或只信任前端布尔值满足前置。

## 3. 状态与重复请求

| 动作 | 输入状态 | 写入结果 | 成功审计 |
| --- | --- | --- | --- |
| 商家首次派工 | 订单 `RECEIVED`，无有效派工且满足前置 | 新建 `ASSIGNED` 派工，写 `assigned_at`；订单不变 | 一条 `audit_log`，不写自反的订单状态迁移 |
| 本人首次接单 | 派工 `ASSIGNED`、订单 `RECEIVED`，满足前置 | 派工 `ACCEPTED`、写 `accepted_at`，订单 `IN_SERVICE` | 一条 `order_status_transition` 与一条 `audit_log` |
| 同键同正文重放 | 24 小时内已成功 | 权限复核后返回原成功响应 | 无新增审计 |
| 同键不同正文 | 已使用的键 | `40001`，不修改业务 | 无成功审计 |
| 新键向同一技师重复派工 | 派工完整且为 `ASSIGNED`，订单仍 `RECEIVED`，前置有效 | 返回已有派工，`changed=false` | 无新增成功审计 |
| 新键向不同技师重复派工 | 已有派工 | `40905`，要求刷新，不改派 | 无成功审计 |
| 新键重复本人接单 | 完整派工 `ACCEPTED`、订单为 `IN_SERVICE` | 返回当前结果，`changed=false` | 无新增成功审计 |

已接单订单的新键派工、非施工状态的新键重复接单、任何不一致的历史记录均返回 `40905`。缓存响应是当次成功快照，客户端收到后刷新当前资源；缓存重放仍复核当前身份和资源归属，不因业务后来推进而重做迁移。

订单状态矩阵仍由 `OrderStatus` 统一定义。A5 不增加订单状态，不开放争议恢复、取消退款或从 `IN_SERVICE` 跳回 `RECEIVED`。

## 4. 身份、权限与数据范围

- 商家每次请求校验商家会话、员工 `MERCHANT/ACTIVE` 和有效商家；只列本店候选、读本店派工、派本店订单。
- 技师 JWT 必须是 `staff_account/TECHNICIAN`，subject 为员工 ID，包含有效 `jti`、`merchant_id`、`binding_id`、当前 AppID 与有效期。微信首次绑定凭证不能调用工单接口。
- 技师服务层再次校验会话记录与上述字段一致、未撤销未到期，员工、绑定及商家仍有效；即使绕过网关的测试或命中幂等缓存也不能跳过。
- 技师列表和详情均同时按派工员工、商家、未删除派工和未删除订单过滤；不同技师、不同商家、不存在资源统一 `40400`，角色错误 `40300`，已失效身份 `40100`。
- 【假设】首版技师读取最小工单信息：订单号/状态、项目快照、预约快照、派工状态/时间和允许动作。不得返回车主 ID、手机号、车牌、VIN、核销码、付款流水或接车私有图片 URL。
- A3/A4 接车单和图片权限保持既有车主/商家范围；技师读取接车照片需要后续明确授权契约。所有业务读取与写响应使用 `Cache-Control: no-store`。
- 技师登录信息使用独立会话对象，跨页面有效，与商家/车主隔离；不在日志、URL 或文档保存 token。退出/401 清空会话与页面数据。

## 5. 数据与历史记录

现有 V001 已有 `technician_assignment`：`order_id/merchant_id/technician_id/status`、公共字段、订单唯一键和技师状态索引；V009 已有 `order.assigned_at`。A5.1 不执行数据库变更。

A5.2 新增独立、可重复执行的 V012，预定增加 `assigned_by BIGINT UNSIGNED NULL` 和 `accepted_at DATETIME NULL`，保留原表与订单唯一键，表总数维持 50。首次派工必须写 `assigned_by`，首次接单必须写 `accepted_at`；时间由服务端 UTC 产生，前端以北京时间显示。是否补分页索引以最终查询及执行计划确定。

迁移不得修改 V001、改写历史派工身份或为历史订单补假证据。上线前盘点已有派工：重复订单、商家/员工归属不符、未知状态、逻辑删除占用唯一键、`assigned_at` 缺失或已 `ACCEPTED` 但 `accepted_at` 缺失，均列为人工核对项。此类记录不可自动变成“可接单”或被新派工覆盖。空库按顺序迁移，已有库备份后补 V012；先扩表再上线应用。回滚应用保留新增列和历史审计，不删除已创建的派工数据。

## 6. 事务、锁与竞争

复用 `WriteIntegrityService.execute`：归属复核、业务、幂等成功响应、`audit_log` 在同一事务中提交；接单另写订单迁移审计。授权与资源锁在幂等记录读取之前执行，状态前置在实际变更回调中检查，防止成功重放被旧输入状态误拒绝。

预定共享资源顺序：调用者会话 → 商家身份校验中需要的商家员工 → 商家 → 目标技师员工 → 绑定 → 预约时段 → 订单 → 派工 → 接车单 → 幂等记录。技师接单在商家锁之后锁本人员工与绑定。技师首次绑定、员工码发放/回收也必须统一商家 → 技师员工 → 绑定，不能和派工形成相反顺序。

现有 `StaffCodeOperations` 与 `bindTechnician` 使用员工锁或 JOIN 锁；A5.2 必须复核并调整相关身份写操作，再以真实 MySQL 并发测试证明无循环等待。查询所需商家 ID 可先非锁读取，拿到锁后重新检查员工归属和状态；不得使用第一次读取结果直接授权。新写操作需与现有预约到期、接车和车主决定保持商家 → 时段 → 订单顺序。

竞争结果必须可解释：

1. 同订单不同技师并发派工：最多一条派工成功，另一条 `40905`；`assigned_at` 与成功审计只写一次。
2. 同订单并发接单：最多一次订单迁移；后到的有效本人请求返回 `changed=false`，非本人仍 `40400`。
3. 派工/接单与停用、解绑并发：以取得身份与商家锁后的有效状态为准；资格撤销提交后不得新成功接单，已有派工不消失。
4. 订单有争议时派工/接单拒绝，不新增成功审计；本阶段不新建接单后的异议入口。
5. 任一审计或缓存写入失败：派工、时间、订单状态和另一类审计全部回滚，原键可重试；不得提前向客户端返回成功。

## 7. 界面

### 商家

从本店订单详情进入派工；先显示接车/确认状态、已有派工结果，再提供本店候选列表。候选名称使用已有员工 `account` 标签，不把绑定 ID、手机号或员工码当显示名称。未确认/争议状态给出明确原因；候选为空提示“暂无已绑定微信的有效技师，请联系管理员维护技师账号”。读取失败提示重试，不展示假候选或默认选中首位技师。

选择一位技师后以订单号和员工标签二次确认；提交期间禁用选择与按钮。超时保留请求与幂等键用于重试，选择改变后换新键；成功刷新订单/派工，冲突刷新后重新选择。401 清空商家会话并引导登录，403/404 不保留旧工单数据。

### 技师

保留现有微信登录和员工码绑定；登录后进入“我的工单”。首版按派工状态 `ASSIGNED/ACCEPTED` 筛选，分页加载，显示工单号、项目、预约时间和派工状态。`ACCEPTED` 表示曾接单，不代表订单永远施工中；同时展示订单状态，后续阶段推进后允许查看本人历史工单。

详情只有符合服务端投影 `can_accept=true` 的本人待接工单显示“接单并开始施工”，二次确认后提交；成功刷新显示施工中。已有争议、失效资格或状态冲突不得继续显示可点击按钮。首版没有报工提交按钮，A6 接入后增加。

两端具备加载、空、断网、错误、无权限、禁用和重试状态；`onShow` 刷新、`onHide/onUnload` 使旧请求失效。账号切换及模态确认回调均校验当前 token 与页面代次，防止用新身份提交旧工单。

## 8. 验收矩阵

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| T01 | 本店已确认订单首次派工 | 一条派工、正确员工/商家/派工人、`assigned_at`、状态仍 `RECEIVED`、一次成功审计 |
| T02 | 派工前置 | 未接车、缺接车单、未确认、字段不一致、争议均拒绝；缺防护不阻断 A5 |
| T03 | 人员资格 | 跨店、非 TECHNICIAN、停用/删除、无绑定、其他 AppID、撤销绑定均不可选不可派 |
| T04 | 本人查询与接单 | 本人可列/读/接；他人、跨店、不存在返回 404；OWNER/MERCHANT/绑定凭证不能访问技师工单 |
| T05 | 接单迁移 | `ASSIGNED→ACCEPTED`、时间成立、`RECEIVED→IN_SERVICE`、双审计一致；商家 `START_SERVICE` 被拒绝 |
| T06 | 幂等与新键重复 | 同键同体原结果；异体 400；重复不写审计；换技师 409；接单重复无迁移 |
| T07 | 真实 MySQL 竞争 | 两人派工、本人并发接单、解绑/停用与操作并发；无重复、无跨身份成功、无死锁 |
| T08 | 失败回滚 | 派工成功审计、接单迁移审计、通用审计或缓存写入故障均整体回滚，原键可重试 |
| T09 | 缓存权限 | 退出/撤销会话、解绑、停用之后已成功键重放仍拒绝 |
| T10 | 页面生命周期 | 翻页/筛选、迟到响应、隐藏、卸载、账号切换、确认回调、断网同键重试；不泄露旧数据 |
| T11 | 契约与迁移 | 严格整数 ID、未知/重复筛选和正文额外字段拒绝；no-store；V012 重复执行；历史异常不自动修复 |
| T12 | 本机端到端 | 隔离店员/两名技师合成身份与真实数据库完成派工→本人查询→接单，并验证另一技师拒绝 |
