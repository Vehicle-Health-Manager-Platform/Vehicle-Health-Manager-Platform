# 接车与履约状态规格（草案）

> 更新日期：2026-10-07｜状态：**关键规则已确认，可实现**。基线：[Spec](../../SPEC.md) §2.2 订单状态与阻断、
> F14/F15/F16/F18。现有实现只有 `PENDING_PAYMENT` / `PAID` / `CLOSED` 三个订单状态
> （见 [预约与订单契约](../../api/RESERVATION_ORDERS.md)），本规格补齐 `PAID` 之后的全部状态。
>
> **决策记录（2026-10-07，用户确认）**：D1 = 预约码；D2 = 仅商家/前台；D4 = 必须车主二次确认；
> D8/D9 = 不自动关闭、由商家或车主显式取消/退款。其余项（D3/D5/D6/D7/D10/D11）采用下方建议默认，
> 标注为**假设**，可随时按用户意见调整。D1/D2/D4/D8/D9 已不再待定，实现不得偏离。
>
> **A2 已实现（2026-10-07）**：§1 的 8 个状态、§2 的矩阵与"前端只能请求动作"、§6 的审计/幂等/
> 行锁已落在代码里，契约见[订单履约状态机](../../api/ORDER_FULFILLMENT.md)。各动作的前置按
> fail-closed 拒绝（未接入校验的动作也拒绝），因此 §3–§5 的业务内容在 A3–A6 接入前，
> 订单实际仍走不出 `PAID`——这是刻意的，不是缺陷。
>
> **为什么先写规格**：状态迁移、操作权属、超时与可逆性属于业务规则，未定就实现必然返工；
> 且 Spec 明确要求"不允许前端直接设置状态"，服务端必须是唯一权威。本草案的默认取值均可改。

## 1. 现有状态与目标状态

现有（已实现，不可破坏兼容）：

| 值 | 含义 | 关闭原因 |
| --- | --- | --- |
| `PENDING_PAYMENT` | 待支付，创建后 15 分钟或时段开始（取早）过期 | — |
| `PAID` | 已付待接车 | — |
| `CLOSED` | 已关闭 | `OWNER_CANCELLED` / `PAYMENT_EXPIRED` |

目标状态（本草案新增，与 Spec §2.2 的数值一一对应）：

| 数值 | 新增枚举值 | 含义 | Spec 原文 |
| --- | --- | --- | --- |
| 0 | `PENDING_PAYMENT` | 待付 | 待付 |
| 1 | `PAID` | 已付待接车 | 已付待接车 |
| 2 | `RECEIVED` | 已接车 | 已接车 |
| 3 | `IN_SERVICE` | 施工中 | 施工中 |
| 4 | `PENDING_VERIFY` | 待核销 | 待核销 |
| 5 | `COMPLETED` | 已完成 | 已完成 |
| 6 | `CLOSED` | 已取消/已关闭 | 已取消 |
| 7 | `DISPUTED` | 争议 | 争议 |

**命名取舍**：沿用现有字符串枚举（而非改成数值），因为 `PENDING_PAYMENT` 等已落库并有对外契约；
数值仅作为 Spec 对照保留。`CLOSED` 继续承载"已取消"，不新增 `CANCELLED` 以免两套语义并存。

## 2. 状态迁移图

```
PENDING_PAYMENT --支付成功--> PAID --商家接车--> RECEIVED --开始施工--> IN_SERVICE
                                 |                    |                    |
                                 |                    |                    v
                                 |                    |            PENDING_VERIFY
                                 |                    |                    |
                                 |                    |        核销 --> COMPLETED
                                 v                    v
                              CLOSED <---------- 任一环节争议 --> DISPUTED
```

允许的迁移（服务端唯一权威，前端只能请求、不能赋值）：

| 迁移 | 触发者 | 前置校验 |
| --- | --- | --- |
| `PENDING_PAYMENT → PAID` | 支付通知 | 已有实现，不改 |
| `PENDING_PAYMENT → CLOSED` | 车主取消 / 到期 | 已有实现，不改 |
| `PAID → RECEIVED` | **待定 D2** | 接车单已完成（见 §4） |
| `RECEIVED → IN_SERVICE` | **待定 D2** | 车主已确认接车单（见 §3）且已派工 |
| `IN_SERVICE → PENDING_VERIFY` | 技师 | 报工记录齐全（见 A6） |
| `PENDING_VERIFY → COMPLETED` | **待定 D3** | 核销成立（见 §5） |
| `任一 → DISPUTED` | 车主 | 车主提异议 |
| `DISPUTED → 前一状态` | **待定 D5** | 争议解决 |
| `PAID/RECEIVED/IN_SERVICE → CLOSED` | **待定 D5** | 退款或双方终止 |

**禁止**：任何跨状态跳跃（如 `PAID → COMPLETED`）；任何前端直接赋值的状态。

## 3. 接车凭证与操作权属

| 编号 | 问题 | 结论 | 影响 |
| --- | --- | --- | --- |
| D1 | 到店用什么凭证接车？ | **已确认：预约码**。车主订单详情页展示 6 位数字码，商家端输入校验 | 一套码同时服务接车与最终核销，只需做一次；车主侧加码展示，商家侧加输入框 |
| D2 | 谁有权执行接车？ | **已确认：仅商家/前台**；技师只能施工报工 | `/api/check/*` 的角色白名单只放 MERCHANT，技师访问返回 `40300` |
| D3 | 核销由谁执行？ | *假设*：**商家**核销；车主只需在订单页看到核销码 | 决定 F08 尾项形态；与 D1 共用同一码 |
| D4 | 接车是否必须车主二次确认？ | **已确认：必须**。Spec §2.2「接车未完成且车主未确认时禁止派工」；异议则置 `DISPUTED` 并阻断施工 | 阻塞 A5 派工：`RECEIVED → IN_SERVICE` 的前置校验里必须包含"车主已确认" |
| D5 | 哪些状态可逆？ | *假设*：仅 `DISPUTED →` 原状态 可逆；`CLOSED` 与 `COMPLETED` **不可逆** | 决定审计与补偿设计；不可逆状态的动作需二次确认 |

**预约码形态（D1 细化，草案）**：6 位数字，按订单生成后固定不变，**不做动态刷新**——因为车主可能在
无网络环境下出示，且 Spec §3.1 的"到店核销码"亦为静态码语义。校验在服务端按订单比对，
**不按码反查订单**（避免遍历猜测），即：商家先打开本店某订单，再输入码校验是否匹配。
**假设**，若你希望改成动态码或扫码，需回到本表修改。

## 4. 接车单要求（F14）

判定"接车完成"必须同时满足（缺一不可，否则不允许 `→ RECEIVED`）：

1. 五向车身照片齐全：前、后、左、右、车顶；
2. 仪表盘照片 + 里程读数；录入里程与档案最近里程比对，**偏差超阈值时给出提示但不阻断**
   （Spec：OCR 失败可人工修正，不阻断流程）；
3. 油量、内饰照片；
4. 已有损伤标注（允许"无损伤"的显式选择，不能默认跳过）；
5. 生成接车单。
6. 通知车主 → 车主确认或异议。

**假设 D6**：里程偏差仅提示、不阻断（Spec：OCR 失败可人工修正，不阻断流程）；阈值初值待定，
实现时以"与档案最近里程的差值超过该车历史波动的合理范围"为提示条件，不硬编码业务含义。
**假设 D7**：五向照片与仪表盘各自独立文件上限，沿用现有"单文件 ≤10 MB、单条档案 ≤5 张"的先例；
接车单是否放宽到 5 向 + 仪表盘 + 内饰共 7 张需在实现时确认。

## 5. 核销与超时

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| D8 | 预约时间与实到时间的偏差如何处理？ | **已确认：不阻断接车**。接车单记录实到时间；偏差超 2 小时要求商家填写原因（*阈值为假设*） |
| D9 | 超时是否自动过期？ | **已确认：不自动关闭**。`PAID` 未接车不自动关闭，避免误关已付款订单；由商家或车主显式取消/退款 |
| D10 | 完成后多久内可评价？ | *假设*：7 天；逾期不再展示评价入口，但不否定已完成 |

D9 的直接后果：**存在长期滞留的 `PAID` 订单**，因此商家端订单列表必须能按状态筛出"待接车"，
并由人工处理。这是有意接受的代价，不是缺陷；若日后要自动化解，需先有退款能力。

Spec 原文只给出 `0–7` 状态与阻断规则，未给出偏差/超时规则；D8 的 2 小时阈值为本文假设。

## 6. 审计与幂等（沿用现有机制，无需新增规则）

- 所有状态迁移写 `order_status_transition` 审计，与业务同事务提交；
- 迁移请求必须带 `Idempotency-Key`（UUID），24 小时内去重，同键重放直接复用响应；
- 同一订单的并发迁移用行锁串行化，第二个请求读到新状态后返回"无状态变化"而非报错；
- 越权返回 `40300`，不存在或非本店/本人返回 `404`，不泄露他人订单；
- 新增错误码建议：`43001` 接车未完成（Spec 已定义）、`43002` 防护照片未上传（Spec 已定义）；
  状态非法迁移建议 `40905`，需与现有 `409xx` 段位协调。

## 7. 对现有契约的影响

- `GET /api/order/list` 的 `status` 过滤白名单需从 3 个扩到 8 个；
- `MerchantOrders` 的 `STATUSES` 常量需同步（当前为 `Set.of("PENDING_PAYMENT","PAID","CLOSED")`）；
- 需新增迁移（建议 V009）：接车单、损伤标注、状态迁移审计、防护照片、技师报工相关表；
- 现有 `appointment_slot` 名额计算使用 `status<>'CLOSED'`，新增状态后**必须复核**该条件
  （已接车/施工中的订单不应再占用名额，或应继续占用——**待定 D11**）。
  **A2 处理**：按 §9 的建议默认实现，即**已接车及之后继续占用名额**，并把口径固化为
  `status <> 'CLOSED' AND (status <> 'PENDING_PAYMENT' OR expires_at IS NULL OR expires_at > now)`
  加真库断言。若日后要改为"接车后释放"，只需改这一处 SQL 与对应测试。

## 9. 决策状态（2026-10-07 更新）

**已确认，实现不得偏离**：

| 编号 | 结论 |
| --- | --- |
| D1 | 接车凭证 = **预约码**（6 位、按订单固定、服务端比对） |
| D2 | 接车权限 = **仅商家/前台**，技师访问 `/api/check/*` 返回 `40300` |

`CLOSED`/`COMPLETED` 不可逆）、D6 里程偏差阈值、D7 照片数量上限、D10 评价 7 天期限、
D11 名额占用口径（建议：已接车及之后**继续占用**名额，因为该时段确实被这台车占用了，
