# R9 A4c-1 数据库恢复演练设计

按既定 A4c 队列先交付可独立验收的数据库恢复单元，再 A4c-2 性能。沿用 brainstorming 的方案梳理和 planning-with-files 的落盘执行方式；用户已要求规划后直接实施。

## 方案

选择 Python 标准库调用 Docker/MySQL 官方工具：本机和 CI 共用入口，直接验证 mysqldump/mysql，避免仅用 JDBC 复制行冒充备份恢复。相比操作既有 Compose 数据卷，两台全新、带本轮唯一标签的 MySQL 容器不接触现有库。脚本不接受数据库地址或已有容器参数；每次 SQL、导出、恢复、清理前核对完整容器ID与归属标签。

## 执行顺序

1. 新建源实例，执行V001–V061；写入合成用户、车辆、档案、LOCAL_TEST订单/付款、会话等，及演练专用触发器、存储过程、禁用事件。
2. 保存升级前逻辑备份及所有表结构/全部列数据摘要。
3. 执行V062后注入SQL失败，证明DDL不会随事务自动回滚；从升级前备份恢复至新库，核对旧结构/数据，不对现有表执行DROP或自造降级迁移。
4. 重试V062并加入合成辅助材料，保存完整备份。恢复至另一台全新MySQL实例，核对全部131表、数据、索引/检查约束、触发器/过程/事件；来源与目标server_uuid必须不同。
5. 损坏源实例的合成里程/档案，证明摘要变化；从完整备份恢复至新库，核对相同摘要；完整迁移重跑前后对比。
6. 验证恢复后唯一约束、CHECK、演练触发器和过程仍有效。失败不得生成PASS。

## 证据与边界

记录镜像/服务版本、迁移及备份SHA256、每表行数和结构/数据摘要、各阶段耗时、两实例标识、清理结果。报告不含行值、口令、令牌或SQL转储。转储仅留.gitignore覆盖的.cache目录，不上传。

逻辑一致性快照只覆盖InnoDB，不支持并发DDL；演练无并发写入、无外部模型/支付/身份调用。备份回退会恢复到备份时点，后续写入必须另做保全，本演练不声称零RPO/PITR。私有对象、病毒库、Redis/RabbitMQ、生产跨主机灾备和旧应用与旧库兼容性不计完成。A4c-2延迟/500并发尚未执行。
