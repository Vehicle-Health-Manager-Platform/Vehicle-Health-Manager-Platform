# 单测试号小程序 S0 设计

> 2026-10-02。用户确认：测试阶段在一个微信小程序测试号内承载车主、商家、技师三种角色；本团队主要负责小程序，PC 运营后台交由其他团队负责。原始交付文档的三种角色能力与业务范围仍是需求来源。

## 方案选择

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 一个测试小程序，按角色分模块（采用） | 当前唯一测试 AppID 可编译、预览和验证三种流程 | 正式三端发布时要分别配置 AppID 并验证身份、路由和权限 |
| 立即申请三个测试号 | 测试环境与原始三端形态一致 | 当前没有三个账号，会阻塞 S0 骨架 |
| 永久合并为一个正式小程序 | 发布和运营入口较少 | 改变原始交付目标，需另作产品决策 |

## S0 工程边界

- 新建独立的 uni-app 3（Vue3）小程序工程；当前 AppID 只用于微信开发者工具构建与测试预览。公开 AppID 可进入非敏感配置，AppSecret 只保存在服务端私有环境变量或 CI Secrets，绝不进入客户端产物或 Git。
- 顶层提供测试阶段的角色入口；车主、商家、技师分别拥有自己的页面目录与导航。测试角色切换只用于预览，不能据此取得业务权限。真实访问由后端根据登录身份、商家归属和技师绑定关系判定。
- S0 只交付可编译、可预览的三角色导航与状态骨架，以及微信登录接口的调用边界；车辆、订单、支付、报工等业务功能按阶段计划实现。未配置服务端时显示明确的不可用状态，不使用假 token 假装授权成功。
- PC 运营后台源码保留为协作资产，本团队不新增其页面或业务实现。小程序与后台共用的 API、角色/资源归属、状态和数据字典仍由本仓库约定；后台团队按 OpenAPI 契约接入。

## 身份与未来拆分

- 客户端调用 `wx.login()` 取得临时 code，发送至 `POST /api/auth/wx-login`；服务端持有 AppSecret、调用微信服务并签发平台会话。客户端不接收 AppSecret 或微信 session_key。
- 测试号下的单一 `user.openid` 可作为当前原始文档基线；正式拆分为多个 AppID 前，增加以 `(app_id, openid)` 唯一的微信身份关联表，并通过已验证的账号绑定流程关联平台用户。不得直接假定不同 AppID 的 OpenID 相同。
- 正式三端 AppID、主体、支付资质、合法域名与提审权限仍是外部依赖；测试号构建成功不代表正式发布和支付验收通过。

## 验收

1. `npm run build:mp-weixin` 可生成小程序产物，工程可导入微信开发者工具，并在三个角色入口之间导航。
2. 小程序代码与构建产物不包含 AppSecret；仓库仅记录公开 AppID 和安全的配置说明。
3. CI 构建小程序并保留现有后端、SQL 与 Compose 验证；PC 后台不作为本团队新增功能的验收项。
4. 进度文档准确区分测试号骨架、未实现的微信登录服务、未取得的正式资质与未交付的业务流程。
