# R9 A4c-2 核心接口延迟与 500 并发基线

## 目标

对原文要求的核心读写门禁给出可复跑、可核验的实际结果：核心读 P95 < 300ms、P99 < 800ms，写 P95 < 500ms，首页/商家列表/订单创建各 500 并发，错误率 < 0.1%。同时把硬件、数据量、预热方式、并发方式和实际失败一起写进报告，不用"本地跑过一次"代替结论。

## 为什么放到独立进程

A4b 的三条旅程在同一个 JVM 内用真实 HTTP 访问随机端口，适合验证正确性，但不适合量延迟：负载客户端与服务端共享 CPU、GC 和线程池，测出来的是两者的合计。本阶段改为：

- 服务端：当前仓库代码打成的 jar，运行在独立容器，JVM 参数、MySQL 连接池大小、镜像都记录在报告里。
- 数据库：本轮新建的 MySQL 8.0 容器，执行仓库内全部 62 个迁移（131 表），只接受随机口令。
- 客户端：独立的多进程负载端。每个进程若干常驻工作线程、每个线程一条 keep-alive HTTP/1.1 连接，所有进程在共享 `Barrier` 上同时开跑，经 Docker 发布的回环端口访问服务端。用多进程而不是单进程 500 线程，是因为 Python GIL 会让单进程客户端先于服务端饱和：实测单进程版本出现 0.002ms 的"成功"响应，测量的是客户端排队而非服务端延迟。

不引入 JMeter/wrk/k6 等外部工具：本机没有它们，CI 也不预装；标准库足以表达固定并发、预热和分位统计，且报告字段可控。

## 三个场景

| 场景 | 请求 | 说明 |
| --- | --- | --- |
| 首页 | `GET /api/vehicle/list` + `GET /api/archive/list?vehicle_id=&page=1&page_size=20` | 车主首页真实发起的两次请求，一次采样=一次页面加载 |
| 商家列表 | `GET /api/service/project/1/merchants?sort=price_asc&page=&page_size=20` | 页码 1/2/3/15 轮换，覆盖深翻页 |
| 订单创建 | `POST /api/order/create` | 每次一个独立时段、独立车辆、独立幂等键 |

订单创建把 500 并发分散到 300 家合成门店：下单链路为了与接车一致，会先锁门店行（`lockShop`），单一门店的并发只能串行。这属于既有设计，不是本阶段要改的行为，所以基线按真实流量形态分布，并把该限制写进报告边界。

每个场景先跑 1 轮预热（同样 500 并发）再统计；读 3 轮、写 2 轮，共 1500/1500/1000 个采样。分位使用 nearest-rank，采样数固定为并发 × 轮次，报告校验会核对该等式。

## 数据量

- 1050 个合成车主、1100 辆合成车辆。
- 100 辆首页车辆各 40 条中文 JSON 档案（4000 档案、4000 附件引用、4000 文件元数据），档案列表一次读取 20 条，附件按 `IN (...)` 一次批量取回。
- 300 家合成门店、1 个标准项目、300 份在架报价、1500 个时段（另加 20 个预检时段）。
- 全部行数写入报告 `dataset`，不接受"空库测性能"。

## 判定

- 错误率：任何非 200、非 `code=0`、结构不符、连接异常都计入错误；错误率必须 < 0.1%。
- 延迟：读场景 P95/P99、写场景 P95 与阈值比较；`--gates all`（默认，本地验收）把延迟作为门禁，`--gates errors`（CI）只把错误预算作为门禁，但延迟照样测量、照样写入报告，并单独给出 `latency_target_met`。这样在 4 核共享 CI 机器上不会因为机器规格把 PR 判红，同时也不会把未达标说成达标。
- 落库：订单数与占用时段数必须等于预热+测量的写入次数，证明响应不是只回包没落库。

## 配置差异

新增 `MYSQL_POOL_SIZE`（默认 10，保持不变，范围 1–200）。500 并发写入时 10 个连接按 Little's law 直接封顶在"10 ÷ 单次事务时间"，必然超出写门禁；基线显式使用 40 并记录在 `environment.mysql_pool_size`。这是容量配置，不是隐藏改动：默认值不变，运维手册给出按目标 QPS 估算连接数的公式。

## 未覆盖

单机、单后端容器、容器内 MySQL，不是生产容量证明；不做长稳、毛刺、故障注入、冷启动和真实网络测量；不把 AI/微信/短信/真实支付放进计时路径；不覆盖小程序 UI 与真机。
