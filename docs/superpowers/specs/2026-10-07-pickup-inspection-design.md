# A3 商家接车检查设计

日期：2026-10-07。状态：设计方案已确认，待用户复核本书面规格。

## 1. 目标与已确认范围

本机完成“已支付订单 → 商家验预约码 → 七张照片与检查项 → 生成接车单 → 已接车”的真实业务链路。复用 A2 的权威状态矩阵、行锁、幂等与同事务审计。

用户已确认：先用手填里程，固定七张照片，一次提交，不保存服务端草稿。车主二次确认仍必须，由 A4 提供；A3 完成后不得开始施工。OCR、短信通知、派工、报工、核销、退款、正式扣款和公网部署不在本步验收范围。

## 2. 方案选择

采用一次提交方案：上传文件独立完成，表单暂存于当前页面，检查单与状态在一个事务提交。失败时保留原图片与原幂等键；身份切换清空表单。

服务端草稿方案可跨设备续录，但需要额外的草稿版本、并发编辑与清理规则。本步不采用。先接 OCR 再交付会依赖尚未落实的识别服务，用户已选择手填版本。

## 3. 角色、入口与预约码

- 商家本店 PAID 订单详情增加“接车检查”入口；仅有效 MERCHANT 会话可填写、上传和提交，TECHNICIAN/其他店铺无权操作。
- 车主本人订单详情展示服务端生成的六位预约码，复用现有 order.verify_code 列；码按订单固定，前导零保留。新订单创建时生成，旧 PAID 订单首次读取本人详情时安全补生成；并发生成用行锁保证固定值，其他状态不得用于接车。
- 商家列表、详情与接车单不返回预约码，商家必须从车主处取得并在提交时校验。请求、幂等缓存、审计及错误响应不得记录明文码。
- 错码统一返回“预约码无效”，不泄漏正确码。按商家身份与订单限制验码频率，10 分钟最多 5 次失败，超过返回 429 和 Retry-After；使用独立失败计数，不随业务回滚而清零。
- 实到时间由服务端取提交时间。与预约开始时间的偏差按 UTC 计算、按北京时间展示；绝对偏差超过 2 小时需填写 1–200 字原因，不限制订单必须当天接车。

## 4. 接车单字段

| 字段 | 规则 |
| --- | --- |
| order_id | 正整数，本店、未删除、已支付；车主与车辆归属由订单读取 |
| appointment_code | 必填六位数字，仅用于验码；不写入接车单或响应 |
| photos | 固定 FRONT、REAR、LEFT、RIGHT、ROOF、DASHBOARD、INTERIOR 七个槽位，每槽一个 file_id |
| mileage | 必填整数 0–9999999 km，来源固定 MANUAL |
| mileage_reason | 比较基线存在且本次里程低于基线时必填，1–200 字；否则可省略 |
| fuel_level | 必选 EMPTY、QUARTER、HALF、THREE_QUARTERS、FULL，界面显示空/¼/½/¾/满 |
| damage_status | 必选 NONE 或 PRESENT；默认不选，禁止自动认定无损伤 |
| damages | NONE 必须为空；PRESENT 为 1–20 项，每项照片槽位、归一化坐标 x/y（0–1）、损伤说明 1–200 字 |
| arrival_reason | 预约偏差绝对值超过 2 小时时必填，1–200 字 |

只接受定义字段；未知字段、重复槽位、重复 file_id、非整数里程、缺照片/油量/损伤选择均拒绝。坐标相对于完整照片，预览缩放不得改变存储坐标；界面在所选照片上点选位置并填说明，可删除后重标。

### 里程比较

优先使用该车最新一条有里程的档案，按发生日期、id 降序；没有则使用车辆 current_mileage。提交时在事务中重新读取并保存比较基线、来源、差值，不采信前端差值。页面显示基线与差值，服务端将它们作为接车单快照。

里程下降必须填写原因，填完允许提交；里程上升展示差值，不推断“异常阈值”。接车读数不自动覆盖车主车辆里程或新建车主档案，避免把尚未由车主确认的读数当作权威档案。

## 5. 商家私有图片

底层复用文件签名/大小校验、ClamAV、私有 MinIO、幂等上传、失败清理与短时签名。当前 HTTP 上传只支持车主会话；本步增加独立商家入口及正式 MERCHANT 鉴权，不把商家转成车主身份。

- 上传路径：`POST /api/merchant/files/upload`，一个 multipart file 字段，UUID Idempotency-Key；JPEG/PNG/WebP，单张 ≤10MB，安全校验沿用现有规则。
- 元数据 owner_type=staff_account、owner_id=上传者 staff id。提交者只能关联本人 CLEAN、未删除图片，七个 file_id 必须互不重复。本人的文件也不得关联到第二份接车单。
- 上传请求增加主体类型作用域，幂等键范围含主体类型、主体 id、请求路径，避免 user/staff 同 id 冲突；限流键同样隔离。既有车主上传协议和档案最多 5 张规则保持其用途。
- 上传前预览：`GET /api/merchant/files/{id}/access` 仅签发当前上传者本人 CLEAN 图片。
- 接车单提交后，本店有效 MERCHANT 或关联订单的本人车主可通过接车单文件访问接口预览；必须同时校验订单归属、检查单与 file_id 的实际关联、CLEAN/未删除。其他店铺、非关联车主、技师、无效会话均拒绝。
- 短时 URL 有效期沿用现有最大 300 秒，响应 Cache-Control=no-store。接车单只保存 file_id，不保存 URL 或 object_key。URL 到期可重新获取；已签发 URL 的访问能力直到其到期，撤销身份后不再签发新 URL。
- 上传失败保留原图和原键重试；重新拍照或更换图片使用新键。七张照片逐张上传；拒绝权限或取消拍照时可返回，不自动提交。

## 6. API

| 方法/路径 | 用途 | 身份 |
| --- | --- | --- |
| GET /api/check/pickup/context?order_id={id} | 可接车订单、预约时间与里程基线，不返回码 | 本店 MERCHANT |
| POST /api/check/pickup/submit | 严格字段检查、验码、生成接车单并转 RECEIVED | 本店 MERCHANT |
| GET /api/check/pickup/{order_id} | 不可变接车单、快照、图片 ID 与损伤标注、待确认状态 | 本店 MERCHANT 或关联 OWNER |
| GET /api/check/pickup/{order_id}/files/{file_id}/access | 关联图片的短时签名 | 同上 |
| POST /api/merchant/files/upload | 私有商家图片上传 | MERCHANT |
| GET /api/merchant/files/{id}/access | 上传者本人预览 | MERCHANT |

提交要求 UUID Idempotency-Key。成功返回 order_id、pickup_check_id、status=RECEIVED、owner_confirm=0、arrived_at 与检查单数据；不含码、完整车牌/VIN、手机号、长期图片链接。重复同键同正文返回原响应；同键不同正文返回 400。验码纳入请求哈希但不保留原值。

已有接车单时新键提交拒绝修改（409），原键重放仍须复核当前角色与店铺。成功接车只产生一次接车单、一次迁移审计及一次业务审计。通用 A2 RECEIVE 动作停止对外开放，PAID 的操作入口改为接车检查；其他履约动作继续使用原接口。

错误沿用统一封套：未登录 401、身份不允许 403、本店资源不存在/非本人资源 404、字段非法 400、当前状态不可接车 409、文件非 CLEAN/无归属 422、验码/上传限流 429、存储/扫描/写入不可用 503。安全错误不含私有细节。

## 7. 数据迁移与事务

新增 V010，可重复执行，新数据卷自动安装，旧本机测试卷先备份再补迁移。

- order 复用已有 verify_code，不新增重复的预约码列，面向商家投影仍排除码。已有订单按安全生成策略补码，生成不修改订单状态、不创建履约迁移审计；此值不写入既有下单审计快照。
- pickup_check 沿用一订单一单唯一索引；增加提交商家/员工、仪表盘 file_id、手动来源、里程基线快照、实到时间及原因。七槽关联使用新 pickup_check_file 表，槽位与检查单唯一，file_id 全局唯一；JSON 中不存图片地址。
- upload_request 增加 owner_type 并调整幂等唯一索引；历史行设为 user，清理任务继续按 request_id 关联。
- 验码失败限流复用独立限流存储，主体与订单作用域明确，不写成功业务审计。

提交事务按现有顺序锁商家会话/员工/店铺、预约时段、订单，再锁车辆和七个文件（file_id 升序）。复核身份、状态、验码、文件、里程与预约偏差后写接车单/关联，按 A2 矩阵 PAID→RECEIVED，同事务更新 check_in_completed_at、写 order_status_transition 和 audit_log、缓存幂等响应。任一步失败整体回滚，预约名额仍占用。

扫描和存储调用在上传独立流程完成，不放入接车事务。接车单、关联文件均以不可变业务证据展示；后续修订/车主异议单独设计，不能覆盖已提交单。

## 8. 小程序交互

商家订单详情进入表单，显示服务项目、预约与里程基线。七个槽位逐项拍照/选图、上传状态、预览、替换和原键重试；固定槽位全部完成才开放提交。明确填写里程、油量、无损伤或损伤标注、必要原因及车主提供的预约码。

点击提交进行一次确认，阻止重复点击；失败显示原因并保留可重试数据。业务成功或返回的不确定成功经详情恢复后展示接车单。切换身份、隐藏页、卸载页时忽略旧响应；身份切换清空照片和码。接车单刷新可重取 URL。

车主订单详情展示本人预约码和接车单查看入口，以页面刷新查看结果，不宣称已发送短信/微信订阅通知；接车单明确“待车主确认，确认功能随后接入”，本步无确认按钮、无派工入口。接车后仍不能开始施工，缺车主确认继续返回 43003。

## 9. 验收

- 后端真库：两店/两车主隔离、TECHNICIAN 拒绝、失效身份、错码与限流、码不泄漏、七槽完整/重复/本人 CLEAN、关联图片访问、里程回退原因与基线重读、预约偏差原因、一单一单并发、同键重放、审计及缓存故障回滚、名额不释放。
- 上传：商家真实扫描与私有存储成功/感染/失败、原键重试、user/staff 同 id 不串、撤销身份、旧车主流程回归。
- 小程序：七槽及损伤标注、取消/权限失败、预览到期、失败重试、重复点击、身份切换与过期响应、无记录和空状态；车主仅可看本人码与单。
- 本机 H5：使用隔离商家身份、真实车主与真实后端/MySQL/MinIO/ClamAV，从测试支付 PAID 实际提交接车单变 RECEIVED，查询两端一致，开始施工仍拒绝。不得手工设置接车时间或 CLEAN 来替代业务链路。
- GitHub 最终提交六项 CI 全绿，记录精确提交和测试数。真机相机/真实短信、正式扣款仍独立待验收。

## 10. 实施分解

1. 商家图片鉴权与上传主体隔离迁移，保持车主上传回归。
2. 预约码、接车字段/关联与事务接口、双角色读取及受控签名。
3. 商家七槽表单与损伤标注、车主预约码与接车单查看。
4. 真库并发/回滚、H5 完整链路、构建/CI与文档收口。
