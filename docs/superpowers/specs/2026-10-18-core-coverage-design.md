# A4a：核心业务覆盖率基线与门禁

依据用户确认的A4顺序，先完成可独立验证的覆盖率，再A4b端到端、A4c性能/备份恢复。不把本单元计作整个A4完成。

## 选择与范围

采用独立Maven覆盖率profile + 固定范围清单 + Python XML门禁。仅列测试数量无法说明执行覆盖；一次性IDE报告不可复跑，因此使用固定版本JaCoCo对真实测试运行插桩，生成可审查报告并加入CI。

- 逐组固定券、邀请、考核、里程及预约/施工/核销关键状态类；完整纳入所声明类及内部类，不临时删掉低覆盖方法或移动阈值。
- 依据原文“核心业务方法”要求，同时衡量LINE和METHOD，要求两者总体与每组均至少70%；同步报告BRANCH但不把其作为本次70%口径。明确未覆盖的其余平台模块，不声称平台全量70%。
- 全量CI测试生成覆盖率；本机先运行明确列出的核心真实MySQL/HTTP/领域套件，覆盖不足时补有实际业务风险意义的用例。
- 缺失报告、清单类未编译/重复归组、无可执行行、未知计数、覆盖不足一律失败。使用整数比较，不通过显示百分比舍入放行。
- Maven profile使用单fork、独立agent文件和报告目录，防止多个进程覆盖报告；运行器清理旧报告并记录精确命令、源提交、测试数量、耗时和环境。
- 不修改业务API/SQL或放宽行为；不连接正式服务，不把本机隔离数据库覆盖率当微信/识别/支付验收。原数据库测试继续真实执行，禁止以跳过测试获得绿色门禁。

## 验收与交付

验证门禁的阈值、缺类、空计数、嵌套类、多组、XML异常等失败路径；实际运行核心套件，记录未通过的具体类/行与修复。报告范围及实际数值随代码/测试/CI/中文文档同批上传。A4b、A4c另行保留，真实外部接口继续B段后置。
