# 单测试号微信身份与角色授权契约（S0 草案）

> 2026-10-02。适用于当前一个测试 AppID 承载车主、商家、技师入口的开发阶段。这里是实现契约，不代表登录接口或真实微信联调已完成。正式拆分 AppID 前必须复核身份映射。

## 身份与权限

| 场景 | 身份来源 | 平台主体 | 签发权限 |
| --- | --- | --- | --- |
| 车主首次登录 | 服务端用一次性 `wx.login` code 换取 `openid` | 按 `user.openid` 查找或创建车主；手机号保持空值，直至另行验证绑定 | 仅车主基础权限；需要手机号的动作逐接口检查绑定状态 |
| 车主再次登录 | 同一 AppID 下的 `openid` | 复用未禁用的同一 `user.id` | 车主权限 |
| 技师首次登录 | 服务端换取 `openid`，再由技师完成商家员工码绑定 | 绑定到现有且有效的 `staff_account`；不能仅凭微信身份新建员工 | 绑定前不签发技师业务权限 |
| 技师再次登录 | `openid` 与有效员工绑定 | 复用绑定的 `staff_account.id`，同时校验员工和商家状态 | 仅该商家的技师权限 |
| 商家入口 | 商家账号登录流程 | `staff_account` 中商家角色 | 不通过 `wx-login` 自动获得商家权限 |

【假设】同一微信账号可以拥有车主和技师两个独立的平台主体。用户切换入口时必须重新请求相应角色的服务端 token；前端入口、`role` 参数和 `openid` 本身都不授予技师或商家权限。技师解除绑定或员工/商家被禁用后，既有 token 在受保护请求时也必须失效或被拒绝。JWT 中包含主体类型、主体 ID、角色和（技师时）商家 ID；业务 API 从已验证的 token 与当前数据库状态取得身份，不信任请求正文中的归属 ID。

## 接口阶段与失败响应

1. `POST /api/auth/wx-login` 请求 `{ "code": "...", "role": "owner|technician" }`。仅服务端持有 AppSecret 并调用微信 `code2Session`；一次性 code 不缓存、不记录日志。拒绝不支持的角色。
2. 车主：以数据库唯一 `openid` 并发安全地查找/创建 `user`。`status=2` 或已删除时拒绝。成功返回访问 token、有效期和 `user` 摘要；手机号未绑定时明确返回 `phone_bound=false`，后续需要手机号的业务接口继续阻断。
3. 技师：未绑定时返回明确的 `BIND_REQUIRED` 状态和短时、仅允许绑定操作的凭证；绑定流程校验商家员工码、员工角色、员工/商家状态与重复绑定冲突。绑定成功后重新签发技师业务 token。无有效绑定时不得返回技师业务 token。
4. `refresh_token` 与撤销机制须有服务端持久化或可验证的轮换方案后再返回；未实现时不得伪造该字段。当前 OpenAPI 草案中的刷新字段仅是目标契约。
5. code 无效返回 HTTP 400；请求过频返回 HTTP 429；微信上游故障返回 HTTP 503；未配置服务端凭据返回 HTTP 503。响应沿用 `ApiResponse`，不暴露 AppSecret、`session_key`、完整上游响应或内部异常。

## 数据与迁移顺序

- 当前 `user.openid` 仅适用于单 AppID；本阶段沿用其唯一约束。创建车主身份须在事务中处理唯一键竞争，不能先查询再无保护地插入。
- 为技师添加独立微信绑定表，至少包括 `app_id`、`openid`、`staff_account_id`、绑定/解绑时间与唯一约束；绑定操作检查员工所属商家与角色。不能把技师的 `openid` 写入 `user.openid` 来冒充车主关系。
- 先提交版本化迁移和空库/重复迁移验证，再实现仓储、绑定流程、JWT 及接口测试。不要直接修改已发布的 V001。
- 正式多个 AppID 上线前，将车主身份也迁到 `(app_id, openid)` 映射表；经可靠的手机号或其他已验证关系绑定同一平台用户，不跨 AppID 假定 `openid` 相同。

## 未决外部条件

真实微信联调需要轮换后的 AppSecret、后端 HTTPS/小程序合法域名和可用测试设备。手机号授权能力、员工码发放与回收、正式 AppID 拆分及刷新 token 失效策略需要后续确认；当前自动化测试只使用伪微信响应。
