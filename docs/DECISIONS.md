# 决策记录

## 2026-10-10：三端业务优先，正式身份接入后置

用户明确要求正式短信、真实微信登录等最后实现，先完成车主/商家/技师其他功能。R0.2b 正式短信与 R0.3 真实身份/真机不再是 R1–R8 开工门槛；先 R1a 入驻，再员工/基础数据、交易业务、车辆档案、健康 AI/服务、券、邀请、进度消息、积分考核社区，最终统一正式身份、真实资金、网络设备和发布验收。业务权限校验继续，隔离联调不进入正式登录流程；短信未配置保持拒绝。PC 运营后台继续取消，必要管理能力在微信受限运营入口实现。详见 [三端规划](progress/THREE_ROLE_BUSINESS_PLAN_2026-10-10.md)。本决策改变实施顺序，不改变历史完成状态。

## 2026-10-09：用户明确缩减为微信小程序交付

用户要求根据缺口和当前进度规划，并明确“不需要完成 PC 运营后台，完成微信小程序部分就行”。该指令覆盖原文及旧 Spec 的 PC 终端交付要求：PC 业务页面、浏览器/断点兼容与 PC 站点发布不再列为欠缺或上线门禁。原交付文档保留原文，不修改历史事实。

车主、商家、技师微信小程序及必要后端仍需完成；【规划建议】审核、基础数据维护、券池与统计等必要运营能力延续已有独立运营身份，放在小程序受限入口。H5 只保留现有辅助验证资产，本路线不新增 H5 交付项目。总路线见 [微信剩余交付路线](progress/WECHAT_DELIVERY_ROADMAP_2026-10-09.md)，各业务阶段仍须形成详细规格后实施。本次仅完成路线与范围文档。

按交付文档 §13，在实现中遇到未定义或互相矛盾的规则时，追加：

`[日期] 【假设】问题 → 决策 → 理由 → 影响的需求/接口/表`

Spec G01–G07 是待形成契约的来源缺口，不能直接视为已经决定。

## 2026-10-08：A5 派工与技师接单实施基线

用户收到 A5 建议计划后要求“开始下一步”，本次交付 A5.1 规格与中文实施计划。以下【假设】是采用的工程默认，不记录为用户逐项确认；完整规则与验收见[A5 规格](superpowers/specs/2026-10-08-a5-dispatch-design.md)。

- 【假设】一单一位技师，仅首次派工与本人接单；改派、撤回、拒单和多人协作另行设计。
- 【假设】候选为本店有效 TECHNICIAN 员工且当前 AppID 已有效绑定微信，无需在线会话。`technician_id=staff_account.id`，不是绑定 ID，解绑不改写历史责任归属。
- 【假设】派工写 `assigned_at`，订单仍 `RECEIVED`；本人接单使派工 `ACCEPTED`、订单 `IN_SERVICE`。A5.2 同时拒绝商家通用 START_SERVICE（43004）并移除其投影，保留状态矩阵。
- 按 Spec F15/§2.2 在 A6 报工时阻断缺防护，修正 S0 草案“防护齐全才派工”；派工和接单仍检查接车证据、车主确认及无争议，不补假时间或假防护。
- 【假设】技师首版只读最小工单投影，不新增接车私有图片、核销码、车主 PII 的授权。
- 统一身份写操作商家→技师员工→绑定锁顺序，兼容派工/接单；撤销后缓存重放仍复核权限。V012 仅预定扩充派工人/接单时间，A5.1 不执行迁移。
- A5.1–A5.5 各完成子阶段整理文档并推送 PR；依赖未合并时基线为直接前序分支，依赖合并后调整至 main 并复核 CI，不自动合并或部署。

## 2026-10-02：单测试号三角色工程与团队边界

用户确认测试阶段在一个微信小程序测试号内预览车主、商家和技师三种角色。本仓库新增一个 uni-app 小程序工程，角色页面和后续业务模块分开；测试入口仅用于预览，业务身份由服务端校验。原始交付文档的正式三端目标暂不改动；正式 AppID 的数量、主体与发布权限仍待确认。PC 运营后台交由其他团队负责，本团队维护小程序及其共用 API/数据契约，不新增 PC 后台业务页面。具体边界见[单测试号设计](superpowers/specs/2026-10-02-single-test-miniapp-design.md)。

单一 `user.openid` 仅维持当前原文与测试号基线；正式拆成多个 AppID 前须新增 `(app_id, openid)` 身份映射，并通过已验证的绑定流程关联平台用户。AppSecret 仅服务端持有，不进入仓库与客户端。

## 2026-10-02：恢复原始交付文档的终端方案

用户决定重新按提供的原始 v1.0 交付文档开发；仓库根目录的交付文档已按该文件原样恢复。车主端为微信小程序主端、H5 兜底，商家端和技师端为微信小程序，运营后台为 PC 网页。车主以微信 code 换 openid 并绑定手机号，技师以微信授权登录并首次绑定商家工号；来源核心接口恢复为 `POST /api/auth/wx-login`。原始 `user.openid` 与可空 `phone` 重新成为数据基线。支付、测试、构建、审核发布和外部资源清单均以原始文档的小程序要求为准。

下方 2026-09-29 的四端网页决定已被本决定取代。此前交付的 Vue3/Vite 车主、商家、技师网页仅是过渡期原型及 CI 验证资产，**不能计为小程序工程、微信登录、H5 兜底或 M0 终端验收通过**。运营 PC 网页、Java 后端、数据库与基础设施可在核对后沿用；小程序工程、真实微信接口和相关验收尚待实施。

## 2026-09-29：四端改为网页（历史记录，已被 2026-10-02 决定取代）

用户明确要求车主、商家、技师和运营四端均以网页交付，并同步修改文档中的小程序要求。S0 按 Vue3 + Vite 构建四端响应式网页；车主、商家、技师优先适配手机浏览器，运营端优先适配桌面浏览器。网页登录改为手机号验证码（运营端保留账号密码与二次校验）；原 `/api/auth/wx-login` 改为 `/api/auth/login`。支付渠道须选择支持浏览器网页的方案，具体服务商与回调契约仍待 S0 确认。原文中扫码进入订单可由浏览器打开二维码链接实现。此变更影响 F01、C01、认证接口、用户表、前端构建、兼容性测试和发布流程。
