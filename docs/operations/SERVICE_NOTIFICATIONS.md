# R7 站内订单消息使用和恢复

## 使用

- 车主、门店、技师从各自角色首页进入“站内消息”。查看当前身份的事件提示、发生时间、订单当前状态及未读数；可逐条标为已读或进入既有订单详情。
- 门店店长/店员共享本店消息与已读状态。技师被转派、解绑或停用后旧范围不可继续读取，新技师不接收旧事件回填。
- 空列表表示当前可见范围无事件，不表示旧业务一定没有发生。原六类埋点从V045开始，关单/退款/异议新增埋点从V047新版开始，共十七类；迁移不回填历史消息。退款受理提示“等待渠道确认”，只有可信隔离渠道结果能提示退款成功/失败，测试交易不代表正式到账。退款不发给技师。
- 网络未知时“重试原已读操作”保留原消息及键，禁止并行重复提交。页面隐藏可在同身份页面实例保留未决内存；退出/卸载后重新读取实际已读状态。切号/换身份清空页面，不恢复他人消息。

## 运维

1. 先按序应用V045–V047再启动新版后端；Compose初始化已挂载。保留原notification及审计，V047扩展来源唯一键并保留旧行ONCE，不默认生成任何历史业务事件。迁移和应用升级应在维护窗口依次完成，旧版程序尚未升级前不要产生多轮新事件。
2. SERVICE_NOTIFICATION_DELAY_MS默认5000，每次最多20事件。业务提交成功即持久保存事件，投递失败不丢失；事件保存失败则业务整体回滚，须以原业务幂等键重试。支付回调保持原可信渠道重试流程，不生成伪成功通知。
3. 待投递行PENDING；成功为DONE并写completed_at。失败记录DELIVERY_UNAVAILABLE、attempts、next_attempt_at，最大退避300秒。首次投递时间与恢复扫描均采用后端业务时钟，不混用数据库默认墙钟。先查数据库可用性和notification约束；不手工填自由文本或私有URL，不把失败直接改DONE。
4. 多实例共用事件锁和通知唯一键，整事件原子投递；重启可恢复。已经写入的合法接收人保持事件时点范围，当前失权由读取实时过滤，不修改事件为后来接手者补推。
5. 只提供站内通知。正式短信/微信身份及订阅消息仍R9；异步诊断和文字本机恢复已在R7c2/c3第一步完成，诊断消息接续下一步，整R7完成前无GitHub上传。

协议见[API](../api/SERVICE_NOTIFICATIONS.md)，实际验证见[验收](../testing/LOCAL_R7C1_NOTIFICATIONS_ACCEPTANCE.md)。

## R7c3 来源排查

退款申请/撤回/店长决定按 refund:ID:revision 区分，多轮申请必须保留多条；渠道结果按 refund:ID:SUCCEEDED/FAILED 区分，多次同结果回调不重复提示。异议提出按 dispute:ID，门店处理和车主复核按 record:ID，关单按 ONCE。同一业务事务内接收人固定，不在投递时重选、不依据当前状态扫描补消息。投递失败沿用独立事务/退避与原键恢复。
