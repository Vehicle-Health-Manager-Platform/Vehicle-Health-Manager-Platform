# 诊断消息使用与恢复

## 使用

- 车主从本人诊断留言页进入“诊断站内消息”；运营从诊断工作区或受理配置页进入。只显示当前仍可见的消息及未读数，可标已读、进入记录或管理队列。
- 管理队列提示包含记录编号，按编号定位当前记录；不会打开正文。处理人员的CASE入口也由详情服务重新核对当前分配/权限，不能用旧通知绕过撤权。
- 本月资格失效不阻止本人读已有答复，新的追加仍按当前资格/受理规则复核。转派或撤销处理权限后旧处理消息不可见；若同时保留当时的管理用途和当前管理权限，只显示队列提示。
- 网络未知时重试原已读操作；重新进入可读取真实read_at。读过的消息不会再次改时间或重复审计。切号、隐藏和权限变化立即清空页面，不能恢复他人内容。

## 升级和投递

1. 先按序应用V048再启动新版应用；Compose包含48个有序SQL挂载，当前104表。两个新表不回填历史接收人、不授予任何运营权限。管理/处理权限仍通过已确认的离线operator-admin维护。
2. 和订单消息共用SERVICE_NOTIFICATION_DELAY_MS（默认5000），但来源表和逐事件投递独立；每批最多20，PENDING可恢复，全部接收人写入与DONE同提交。不要将失败直接改DONE、手工补自由正文或复制他人历史通知。
3. 失败仅记录DELIVERY_UNAVAILABLE、attempts和next_attempt_at，退避最长300秒，无永久丢弃。恢复实例从捕获目标投递，不能根据现在的运营名单补发旧事件。首次投递及扫描采用业务时钟。
4. 消息写入失败必须使诊断业务事务回滚；原业务键可重试。排查先查迁移、来源/接收人唯一约束、notification约束及数据库可用性，再核对case_event/通知来源及捕获用途。禁止把诊断正文或完整SQL错误写入通知payload/普通日志。
5. 消息总数、未读数和已读均按相同当前用途过滤。消息原始行存在不保证现在可见；重新分配或重新授予权限也不把旧管理用途提升为正文用途。
