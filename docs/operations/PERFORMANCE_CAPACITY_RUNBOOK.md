本文件说明如何用本仓库的性能基线结果做容量判断，以及哪些结论不能从基线里推出来。

## 何时使用

- 上线前或重大改动后复核核心读写的延迟与错误预算。
- 调整数据库连接池、实例规格、并发上限前，先取得可对比的基线。
- 排查"接口变慢"时，先看基线报告的分位与错误分类，再决定是否改代码。

## 执行环境要求

- 与验收报告记录的硬件一致才有可比性：CPU 逻辑核数、内存、Docker 版本、MySQL 镜像、JVM 参数、连接池大小都会显著影响结果，报告里逐项记录。
- 同一台机器上不要同时跑后端全量测试、小程序构建或其他容器负载，否则分位会被邻居负载污染。
- 不要为了"跑过"而降低并发或只挑低负载时段：报告校验强制并发为 500，且 `latency_target_met` 会如实记录未达标。

## 连接池估算

500 并发写入时，可用连接数直接决定吞吐上限。按 Little's law：

```
所需连接数 ≈ 目标 QPS × 单次事务耗时(秒) × 安全系数(1.3)
```

示例：目标 1000 QPS、单次下单事务 15ms，则约需 20 个连接，取 26。默认 `MYSQL_POOL_SIZE=10` 适用于常规流量，不是 500 并发的容量配置；基线显式使用 40 并记录在报告里。调大连接池必须同时确认 MySQL `max_connections` 与实例 CPU，盲目堆连接会把瓶颈从池转移到数据库。

## 预约席位计数（reserved_count）

预约名额不是"每次下单统计一遍订单"，而是按时段行上的计数判断，否则高并发下会把整张 `order` 表锁住。

- 语义：`appointment_slot.reserved_count` = 该时段**未关闭**订单数（含已过期但尚未被关闭的 `PENDING_PAYMENT` 占位）。
- 维护：写入路径在持有**时段行锁**时增减——下单 +1，关单/退款取消 -1，从不按范围统计。
- 展示：接口返回的 `capacity_left` 仍由订单表现算（排除已过期未关闭），所以过期占位在下一次读取时立刻释放，不必等 30 秒过期扫描。
- 判定：下单时先关闭该时段已过期的占位，再用"计数 − 本次关闭数"与 `capacity` 比较，语义与旧实现一致。
- 为什么不做 `SELECT ... FOR UPDATE` 统计：`order` 行数少时优化器会选全表扫描（`EXPLAIN` `type=ALL`），加锁范围覆盖全部订单行和 supremum 记录，等于把下单串行化，并与并发插入互相死锁；行数多时改走 `idx_slot_status_expiry` 范围锁，仍会锁到相邻时段的间隙。两种都不接受。
- 校准：只有从 A4c-2 之前的数据升级时才需要执行一次（新库由代码维护，天然精确）。执行前先停下单写入：

```sql
UPDATE appointment_slot s SET s.reserved_count=(
  SELECT COUNT(*) FROM `order` o WHERE o.slot_id=s.id AND o.is_deleted=0 AND o.status<>'CLOSED');
```

## 结果解读

1. 先看错误率与错误分类：`http_5xx` 说明服务端异常，`transport` 说明连接层问题（超时、端口耗尽、容器重启），`unexpected_payload` 说明协议或数据准备有问题。任何一类都不应被延迟数字掩盖。
2. 再看 P95/P99 与阈值：读 300/800ms，写 500ms。P99 明显高于 P95 通常指向连接池排队、GC 或锁等待。
3. 交叉核对 `database_after_load`：订单数与被占用时段数必须等于写入次数，否则"快"可能只是没真正落库。
4. 订单创建按门店分布测量。单一门店的高并发会在门店行锁上串行，这是与接车流程统一的锁顺序，不应通过去掉锁来"优化"。
5. `cleanup` 全部为 true 才算这次执行可信；有残留就按本轮目录里的容器名人工确认后再重跑。

## 不能得出的结论

- 不能把单机容器结果当作生产容量上限或 SLA。
- 不能把 CI（共享 runner、`--gates errors`）的分位当验收结论；CI 只保证错误预算与脚本可执行。
- 不能外推到长稳、尖峰衰减、故障切换、跨可用区网络、冷启动。
- 不能外推到真实 AI/微信/短信/支付链路：这些外部依赖不在计时路径内，延迟必须单独在 B 段测量。

## 复验触发条件

- 核心接口 SQL、索引、事务边界或锁顺序变化。
- 连接池、Tomcat 线程数、JVM 堆参数变化。
- 迁移新增表/列影响热点查询。
- 发布前 R9-C 复验（正式环境需要重新测量，不能沿用本机数据）。

## 2026-10-30 后续优化结果（优先于上方历史状态）

JFR和MySQL语句摘要定位报价COUNT扫描及连接等待；已减少报价重复连接、合并只读会话校验和预约事务中的重复SQL，保留行锁、幂等、佣金和审计。连接池保持40，不采纳扩池掩盖问题。
