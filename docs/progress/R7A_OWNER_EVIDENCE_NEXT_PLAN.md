# 下一步：R7a 车主施工证据与进度

整 R6 的[需求销项](R6_REQUIREMENT_CLOSURE.md)及最终六项 CI 核验完成后，从本人订单施工证据开始。这里只规划下一阶段；不把计划接口计为已实现。

## 已有代码与缺口

`ServiceWorkController` 已有商家和技师的施工详情/文件签名读接口；`ServiceWork` 已有防护、三类照片、方案配件工时、质检签字和核销前完整性校验。车主订单详情已有接车单、状态、核销及归档入口，尚缺完整施工证据和取车前后对比。复用这些事实，不另造一套施工状态。

## 分步实施

1. 本人订单只读投影：在现有订单归属检查上补车主施工证据读取，限定防护/施工/故障件/完工/质检事实；不暴露员工账号、微信、原始文件地址或其他客户资料。草稿、已提交、已签字及历史缺证据分别显示真实状态，不能把状态标签当图片已齐全。
2. 私有文件访问：每次请求重新检查当前车主会话、当前订单归属、订单/证据关系及安全扫描/删除状态，再签短期访问；拒绝把任意 file_id 传入即签名。复用已有短期签名策略，并把撤权后拒绝新签与已签链接残余期限明确记录。
3. 页面与对比：本人订单增加施工进度/证据入口；按现有证据分类查看，取车前接车照片与完工证据明确来源，不编造同角度配对或缺失图片。账号/订单切换、隐藏和读失败清除旧私有数据，重试不触发任何施工写操作。
4. 验证及文档：真实 MySQL/HTTP 权限、跨车主/订单猜测、文件移除/不安全、历史缺证据、状态兼容和当前会话撤销；前端异步隔离/读取失败及微信/H5构建。维护协议、使用、运维、验收和需求销项，完整阶段代码与文档同批上传并核对最终 CI。

## 边界与顺序

商家/技师聚合工作台及最小必要档案接续 R7b；可靠站内通知、非实时诊断留言/分配与写入恢复接续 R7c，接受留言时在服务端事务重新复核 R6 当前资格。人工在线客服不在本规划。积分/考核/经营与社区来源检索在 R8；供应商识别、正式短信/微信身份/资金、真机及发布交付最后 R9。
