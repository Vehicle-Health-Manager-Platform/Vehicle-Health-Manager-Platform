# 微信小程序剩余交付路线

> **2026-10-10 顺序覆盖**：用户要求先完成三端其他业务，正式短信和真实微信登录等最后实现。当前路线以 [三端业务优先规划](THREE_ROLE_BUSINESS_PLAN_2026-10-10.md) 为准；R1–R8 不再依赖 R0.2b 正式短信/真实员工绑定通过，下一单元 R1a 入驻。本文下方原 R0 优先与 R1 正式短信前置为历史安排，已被覆盖；业务权限仍必须验证。


日期：2026-10-09。规划基线：交付缺口审计 `fe64008`，包含 A7.2c2 已实现代码。本文是后续阶段路线，未执行新功能编码或验收。

## 1. 当前范围

用户本次明确：“不需要完成 PC 运营后台，完成微信小程序部分就行”。因此：

- 交付车主、商家、技师微信小程序业务，以及支撑它们的后端、数据库、文件服务与部署。
- **PC 运营页面、PC 浏览器/断点兼容、PC 静态站点发布移出交付门禁**；不作为剩余欠缺功能。
- 运营审核和维护仍是入驻、发券、内容与基础数据业务的必要依赖。推荐延续已实现的独立运营身份，在同一小程序的受限运营入口完成这些能力；“取消 PC”不等于取消审核权限与运营业务。
- H5 保留现有辅助验证资产，不安排新增 H5 页面或独立 H5 上线项目；正式交付证据以微信原生和真机为准。
- 当前单测试号工程继续使用，正式 AppID/主体/角色绑定及发布配置作为上线前置条件；不提前假定需要多个新小程序。
- 既有七图接车、确认/异议、派工、报工/签字、核销、评价、私有卡片/审核能力沿用。第二次异议与超时自动处理仍不增加到本轮范围。

原始交付文档保持原文，新的终端范围由 [决策记录](../DECISIONS.md) 与更新后的 [Spec](../SPEC.md) 覆盖。原 [缺口审计](DELIVERY_GAP_AUDIT_2026-10-09.md) 的 PC 缺口是变更前的对照结果。

## 2. 路线选择

| 路线 | 顺序与代价 |
| --- | --- |
| 推荐：先验证履约，再补业务依赖 | 原生验收→入驻/运营基础→资金→车辆健康/AI→券/邀请→P1→上线；减少新业务叠加到未经原生验证的基础上 |
| 增长优先 | 先券/邀请；展示效果较早，但正式入驻、收退款与运营数据不全，容易重做资金和权限联动 |
| 健康/AI 优先 | 先首页和诊断；车主体验较早完善，但仍无法形成可开店、可收退款的运营闭环 |

采用第一条作为建议执行顺序。以下各阶段是独立项目，每阶段先形成自己的中文业务规格，再拆后端、微信页面和联调；总路线不替代尚未确认的支付、奖励、考核等详细业务规则。

## 4. 当前立即可执行的下一单元：R0.1

复用 [原生验收安排](../superpowers/plans/2026-10-09-wechat-native-acceptance.md)，先完成工具连接和原生页面基线：

1. 核对当前分支/产物、AppID、工具版本、工具 HTTP 服务端口与自动化 WebSocket 端口，复用 `apps/miniapp/test/simulator-smoke.cjs`。此前端口混用只是待验证假设，不当作已确认根因。
2. 成功建立自动化连接，记录实际页面路径与断言；登录入口、角色切换、未授权访问、已实现业务路由均须在微信产物验证。
3. 连接隔离真实后端/数据库走授权→审核→同款查看→撤回，以及现有履约主链路；合成会话仅用于隔离数据，不记为真实微信账号通过。
4. 核验选图/上传、签字与图片访问；修复实际暴露的问题。模拟器不具备的物理相机/手机号/短信/手机网络能力单列待验收。
5. 输出 `docs/testing` 下中文原生验收记录及阶段执行记录，更新当前状态/下一步/缺口，提交阶段 PR 并核对最终 head 的 CI。

R0.1 门槛：**实际自动化握手 + 原生页面操作 + 真实接口/数据结果**。仅 CLI import/auto 返回成功、H5 操作或微信构建成功均不足以通过。

R0.2：接入商家/运营正式短信适配并验证一次性码、限流、失败与撤销。R0.3：真实微信账号及 iOS/Android 验证登录/手机号、相机、图片、签字、履约、审核/撤回。正式供应商或设备未到位时，继续能独立执行的规格/代码工作，保留未验收状态；不假定完整 R0 已通过。

## 5. 各阶段的拆分方式

每阶段依次交付：

1. **规格**：页面与流程、角色权限、状态/错误、外部依赖、数据与隐私、验收场景；原文不明确的规则形成明确方案并经复核。
2. **后端**：最小数据库迁移、接口契约、幂等/事务/审计/权限与对应验证。
3. **微信页面**：沿用 `apps/miniapp` 与现有身份，不用 Web 空骨架替代；空/错/加载/重试/授权拒绝场景齐全。
4. **联调与收口**：真实接口/数据库、原生操作、相关回归/构建/CI，中文记录列明真实服务、合成数据和外部待验收项。

阶段大于单个可审阅 PR 时，按规格→后端→页面→验证分别上传。每个 PR 只包含该阶段差异。后端可以先用确定性接口模拟供应商进行开发，但正式短信、资金、识别服务验收必须独立记录。

## 6. 实施前必须形成详细规则的项目

- 资金：退款资格、部分退款首版是否支持、取消截止点、退款失败恢复、支付异常；免佣起算与佣金基数，资金处理的权限。
- 券/邀请：券类型/库存/叠加/门槛、退款返券、月度时区、奖励模板、有效新用户、归因与防刷。
- 健康/AI：车型规则和知识来源、指标无数据的展示、不生成虚假评分；公开评价授权与统计口径，RAG 只检索获准公开数据。
- 考核：40/40/20 权重保留，标准化方式、周期、等级阈值必须有可复算规则；不凭权重猜测完整算法。
- 档案：完成事件与既有评价任务共存的唯一约束、失败恢复、历史订单策略；不能重复生成或覆盖原始手工记录。

这些是各阶段规格任务，不预先记为已确定或已编码。本路线不以供应商密钥到位时间估算固定交付日期。

## 7. 外部依赖与推进方式

## 8. GitHub 与完成口径

- 沿用 [阶段上传规则](STAGE_DELIVERY.md)：每完成一阶段，同步中文文档、提交 `codex/` 分支、推送 GitHub、创建 PR、核对最终 CI。
- 当前前序未合并时，PR base 指向直接依赖。合并时按链逐支落入 main，再将下一支 base 改回 main；不合入上一功能分支。
- 开始新实现前读取实际 GitHub 状态与 main，避免以历史记录推断前序已合并。上传授权不等于合并或生产部署授权。
- 区分已规划、已编码、已上传、阶段验证通过、已合并、真实环境验收通过、已发布。现有 A7 默认关闭功能必须在发布阶段检查迁移、客户端、开关与回滚。
- PC 不再出现在未完成项与最终兼容验收中；小程序运营业务、后端安全与运维门禁继续计入。
