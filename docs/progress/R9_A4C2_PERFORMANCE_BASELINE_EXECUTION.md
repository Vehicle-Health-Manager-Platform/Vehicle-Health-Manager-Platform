# R9 A4c-2：核心接口延迟与 500 并发基线

2026-10-18。前置PR162；分支 `codex/r9-a4c2-performance-baseline`。**本轮结论：错误预算达标（三个场景 4000 次采样零错误、写入全部落库），延迟门禁未达标**（读 P95 590/684ms、写 P95 614ms，阈值 300/300/500ms）。原因已定位为本机 CPU 打满，不是连接池配错，也没有通过降并发或挑低负载时段掩盖。

## 本轮实现

- `scripts/run_performance_baseline.py`：Python 标准库 + Docker；每轮新建带随机标签的网络、MySQL 8.0 和后端 jar 容器，所有操作与清理都核对完整容器 ID、名称、角色和本轮标签。独占发布端口，不连接任何既有数据库或业务凭据。
- 执行仓库全部 62 个迁移（131 表），灌入固定 ID 的合成数据 13320 行（1050 车主、1100 车辆、4000 档案、4000 附件、300 门店、300 报价、1520 时段、1050 会话）。
- 负载端 10 个进程 × 50 常驻线程，共享 `Barrier` 同时开跑，每线程一条 keep-alive HTTP/1.1 连接；绕过单进程 GIL，避免测到客户端自身的排队。
- 每个场景先 1 轮预热再统计；读 3 轮、写 2 轮。分位用 nearest-rank，报告校验采样数必须等于并发 × 轮次，并发必须为 500，阈值不得漂移，结论必须与检查项自洽。
- `scripts/test_performance_baseline.py` 14 项单测；`schema-and-ocr` job 增加该单测，新增独立 CI job `performance-baseline`（`--gates errors`，45 分钟超时，上传 artifact）。
- `MYSQL_POOL_SIZE` 可配置（默认 10 不变，范围 1–200），默认与容量配置的区别写进 `environment.mysql_pool_size` 与运维手册。

## 未达标的原因

1. **CPU 打满，不是池大小。** 验收运行里后端容器峰值 925.4%（首页）/723.5%（商家）/885.2%（下单），MySQL 峰值 182.2%/1014.4%/475.1%，两者相加已到 10–18 核，本机再跑 10 个负载进程，24 核被完全占用。
2. **连接池只解释首页的一部分。** 池 40 时首页 `hikaricp_connections_pending` 峰值 130（Tomcat 200/200 全忙）；池 80 后首页 P95 从 590 降到 432ms、等待归零、后端 CPU 反而升到 1198.9%，说明瓶颈从池转移到 CPU。商家列表在池 80 时 MySQL 峰值 1404.9%、等待仍有 80，池不是它的瓶颈。
3. **实测并发低于 500。** 下单场景 748.96 采样/秒 × 平均 332.992ms ≈ 249 个在途请求，说明本机客户端在这台机器上维持不住 500 个同时在途。因此上面的 P95 是**偏乐观**的下界，真实 500 并发客户端会更差，不能反过来当达标依据。
4. **`server_metrics` 采样点太少。** 每个场景只有 1–2 个采样点（场景本身只持续 1–2 秒），只用于判断瓶颈方向，不作为容量结论。

要在这台机器上把读 P95 压到 300ms 以下，需要的不是继续调池，而是同样的请求量下多一倍 CPU（多实例/更大规格）或显著减少单请求工作量（首页一次页面加载是车辆列表 + 20 条档案，含 60 次 JSON 解析）。这属于下一段容量工作，本轮不假称已达。

## 调试记录

1. 单进程 500 线程先饱和：出现 0.002ms 的"成功"响应，测到的是客户端排队。改为 10 进程 × 50 线程 + 共享 `Barrier`。
2. 首页首次 500 并发出现 30 个 401、1470 个 404：负载映射 `index % 50` 取到 0 号车主（令牌为空）。改为 `index % 50 + 1` 并同步车辆映射。
3. 档案列表每条档案再查一次附件（真实 N+1）：改为一次 `IN (...)` 批量取回。50 并发首页 P95 从 204.926ms 降到 138.182ms，吞吐 217→390 采样/秒以上。
4. 下单被共享目录行锁串行：`quote` 带 `FOR UPDATE` 的 join 对 `standard_project` 取排他锁，全平台下单排队（实测约 50 单/秒）。改为目录行 `FOR SHARE` + 只对门店报价与版本行 `FOR UPDATE OF q,v`。
5. 下单仍大量 503：`WriteIntegrityService` 把任何异常统一包成 503，用 `SHOW ENGINE INNODB STATUS` 抓到死锁——`SELECT id FROM \`order\` WHERE slot_id=... FOR UPDATE` 持整表 next-key 锁与并发 `INSERT INTO \`order\`` 互等。`EXPLAIN` 复现根因：`order` 行数少时优化器选 `type=ALL`（40 行时全表扫描），行数多时才走 `idx_slot_status_expiry`，即加锁范围随数据量漂移。
6. 修正方式：席位判定改为时段行 `reserved_count` 计数（持时段行锁时 +1/-1），统计只用于展示且不加锁。
7. 修正后仍有 42/50 失败：`expireSlot` 用范围 `FOR UPDATE` 关闭过期占位，即使没有过期订单也会锁住相邻时段的间隙（证据：`idx_slot_status_expiry` 间隙锁 vs `INSERT INTO \`order\`` 死锁，锁等待记录 slot_id=40、插入 slot_id=35）。改为先无锁取候选 id、再按主键逐行 `FOR UPDATE`。50 并发下单随即 0 错误、订单全部落库。
8. 有一次 500 并发运行被人为中断，残留的本轮 MySQL 容器与网络按标签确认后手工清理，再重跑取得上面的验收结果。

## 回归与边界

`JdbcReservationsTest` 新增"8 个车主并发抢 2 个名额，恰好 2 成功、6 个 `40903`""过期占位在下一次下单前释放"两例；`JdbcReservationsTest`、`JdbcOrderRefundsTest`、`JdbcPaymentsTest` 共 80 项通过（3 个 Testcontainers MySQL 实例）。

边界：单机单容器、MySQL 与后端同宿主，不是生产容量证明；不做长稳、毛刺、故障注入、冷启动、真实网络；订单创建按 300 家门店分布，单一门店仍在门店行锁上串行（与接车流程统一，不解锁）；AI、微信、短信与真实支付不在计时路径内；小程序 UI 与真机在 R9-C 单独验收。
