# A4d-6 支付退款恢复与佣金验收

日期：2026-10-21。承接A4d-5的六接口缺口队列，设计见[金融恢复验收设计](../superpowers/specs/2026-10-21-financial-recovery-design.md)。用户已授权规划后实施，阶段完成后上传GitHub。

## 实施

- 新增金融套件：六个重点接口及退款申请、店长决定两个支撑接口，共8接口72场景，均有正常/边界/错误/越权分类。
- 使用现有全迁移MySQL及真实Spring后端；扩展隔离运行器启动仅绑定同容器127.0.0.1的Java签名供应商，不修改生产渠道或放宽loopback限制。
- 供应商对退款提交核对原支付、金额、币种、退款号幂等键及HMAC；支付和退款查询返回独立签名回执。
- 验证支付恢复、终态重复核对、坏金额保持未支付、查询租期、退款撤回/重放/重提/旧版本拒绝、审批关闭、查询后提交、FAILED退款只查询不重新提交、唯一冲销及测试/真实账本分离。
- CI加入独立金融套件执行；业务套件互斥，前置源码指纹包含金融定义和Java供应商；私有JWT、Newman原始记录和完整日志只留.cache。

## 数据与边界

身份、基础车型、订单/支付、FAILED退款和原始0.60佣金为明确SQL合成夹具；不是本轮真实微信注册、支付或施工核销事实。支付恢复、当前退款申请/撤回/批准与退款查询恢复通过实际HTTP驱动；冲销由恢复事务产生。仅LOCAL_TEST，所有正式供应商继续后置。

预期供应商调用：支付1查询一次、坏金额支付4查询一次、新退款查询一次/提交一次、历史失败退款查询一次/提交零次；客户端重复核对不能增加这些次数。数据库独立核对恢复次数、事件/退款唯一性、账本冲销、跨归属数据不变和容量释放。
