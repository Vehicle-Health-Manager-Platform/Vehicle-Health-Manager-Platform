## 0. 一句话结论

交易链路此前**止于"已支付"**。阶段 A2（2026-10-07）已把状态机地基铺好：8 个状态成为服务端唯一权威，
商家侧有了动作式状态操作接口、迁移审计与并发行锁；但接车单、车主确认、派工、报工与核销的
**业务内容**仍未实现，因此订单实际还走不出 `PAID` —— 每个动作都会以 `43001`/`43003`/`43004`/`43005`/`43006`
明确拒绝，而不是静默失败或伪造状态。下一步的价值仍是把订单从"已支付"推到"已完工"（A3–A7），
它同时解锁商家端与技师端的全部空白。

此外商家端只有"选品定价 + 时段 + 只读订单查询"，技师端**除了工号绑定没有任何业务页**，
运营端 PC 后台完全未开始。

## 7. 分步实施计划

原则：**每一步都能独立验收、都留可复现证据、不假设未定规则**。履约相关必须先出书面规格
（见 [接车与履约状态规格](../superpowers/specs/2026-10-07-fulfillment-state-design.md)）。

### 阶段 A：把交易闭环从"已支付"推到"已完工"（当前最高价值）

| 步 | 范围 | 为什么这个顺序 |
| --- | --- | --- |
| A1 | **接车与履约状态规格**（书面；2026-10-07 关键规则已确认） | 状态迁移、谁有权操作、超时与可逆性必须先定，否则实现即返工 |
| A2 | 订单状态机与商家接单/状态迁移（F16 前半）| **已完成（2026-10-07）**：8 状态收敛为服务端唯一权威，动作式操作接口、迁移审计、行锁与幂等就位；各动作的前置按 fail-closed 拒绝，等 A3–A6 接入。见[状态机契约](../api/ORDER_FULFILLMENT.md) |
| A3 | 接车检查（F14）：七图、手填里程、损伤标注、预约验码与接车单 | 已合并 PR #34，车主决策前置已具备 |
| A4 | 车主确认接车单与提出异议 | 已验证并上传 PR #35；预约码由 A3 提供，最终核销移至 A7 |
| A5 | 派工 + 技师工作台与接单（F18 前半） | 首次给技师端可用页面，解锁 F18 |
| A6 | 施工/防护/完工拍照、方案、配件、质检签字（F18 后半、F15） | 依赖 A5 的派工归属校验 |
| A7 | 完工 → 核销 → 评价（C25）→ 档案自动更新（F03）→ 经验卡片（F12） | 闭环收尾，一次性解锁 F03 尾项与 F12 |

### 阶段 B：增长闭环（可与 A 并行，规则已在 Spec 给出）

F10 邀请（月循环、双向奖励、已注册不计数）→ F09 券（发/领/核销/过期，错误码 `42001`）→
F11 积分（P1）。F07 的"用券"在 F09 之后补。

### 阶段 C：车主端体验补全

F02 另外三种录车入口（OCR/VIN/车牌，受外部依赖约束）→ F04 评分与五类提醒（**须先定规则**）→
F06 附近商家与评价总结 → C10 商家详情、C12 AI 方案、C24 施工进度页。

### 阶段 D：运营端与考核

F13 入驻与审核 → F20 运营后台 → F19 商家考核（P1）。

### 阶段 E：外部依赖与上线

短信服务商、微信支付商户号、OCR 服务、备案域名、监控告警与安全审计（M6 门禁）。
