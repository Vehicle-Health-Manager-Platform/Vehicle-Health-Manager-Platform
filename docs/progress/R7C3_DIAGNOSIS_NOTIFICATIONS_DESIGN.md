# R7c3 第三步：诊断专属消息设计

按已授权的[下一步](R7C3_DIAGNOSIS_NOTIFICATIONS_NEXT_PLAN.md)实施，不新增业务资格或处理授权。

## 契约和顺序

1. V048 新增诊断通知 outbox 与事件接收人表，共104表。诊断 case_event 在创建/追加/分配/答复/关闭事务内产生后立即捕获通知来源、当时车主、有效获派人及当前有效管理人员。来源 event ID 唯一，无历史回填；队列和正文用途分别标记，同一运营账号同事件一条通知。
2. 接收人查询使用当前锁定读取。诊断写已持有 control 锁；通知已读同样先按原身份锁序处理 owner，再 control，再运营账号/来源，避免与诊断写反向锁序。管理权限仅队列提示；处理资格仅当时获派且现在仍获派者可用。移交者不继承他人旧通知；原本管理接收人若后来获派，其旧管理消息仍仅队列用途。
3. 每事件独立事务投递全部捕获接收人到现有 notification，完成状态一同提交；SKIP LOCKED、多消费者去重、有界退避、重启恢复。不发正文/payload，不在投递时重选接收人。业务与来源/接收人写入失败必须一同回滚。
4. 新增四项 API：GET /api/{owner|admin}/diagnosis/notifications；PUT /api/{owner|admin}/diagnosis/notifications/{id}/read。列表20条分页及未读数；条目仅 notification_id/kind/case_id/case_status/target/occurred_at/read_at，target 为 CASE 或 QUEUE。所有读取/总数/未读/原键已读均复核当前身份与业务用途，无额外默认权限。管理队列无正文，CASE 入口也须详情端再次授权。
5. 车主和运营诊断页面进入独立消息页。严格协议、固定文案、角色/权限/隐藏切换清理和迟到响应隔离；已读用原键重试，重进后可读取真实 read_at，无重复审计。队列入口只跳管理队列，不推定能直接读正文。
6. 验证真实事务回滚/接收人冻结/分配撤权/双权限降级/分页/并发投递/失败恢复/已读重放、HTTP输入隔离/no-store、前端及微信/H5、104表重放与全部API/文档引用。完成后整理执行和验收，接整 R7 统一门禁与销项。

本步不上传，整个R7完成后才统一上传所有代码、迁移、测试和文档。正式渠道、真机及发布仍R9。
