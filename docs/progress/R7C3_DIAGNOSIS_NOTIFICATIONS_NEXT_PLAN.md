# R7c3 下一步：诊断专属站内消息

本计划已本地实施，见[执行与验收](R7C3_DIAGNOSIS_NOTIFICATIONS_EXECUTION.md)；下一[整R7收口](R7_COMPLETION_NEXT_PLAN.md)。

前置为[诊断已实现权限](R7C2_DIAGNOSIS_DESIGN.md)、[本机恢复](R7C3_RECOVERY_EXECUTION.md)及[补充订单消息](R7C3_ORDER_NOTIFICATIONS_DESIGN.md)。沿用用户确认的独立运营处理/管理权限，不新增默认处理人或身份授权。

## 分步实施

1. 检查 CREATED/MESSAGE/ASSIGNED/REPLIED/CLOSED 的实际事务位置，在同一事务捕获新事件接收人及 case_revision，诊断会话独立关联，禁止使用虚假订单。旧 diagnosis_case_event 不推断当时接收人、不回填历史消息。
2. 独立持久来源与去重投递。车主只能取本人；处理人须为事件当时接收人且当前仍获派、有处理权限；管理人员仅获得队列元数据和管理入口，不能凭管理权限读取正文。新分配者不会继承原接收人历史通知。列表、总数、未读、已读与入口全部按同一当前范围复核。
3. 扩展车主消息入口和独立运营消息入口；诊断条目只含业务编号、固定类型、当前状态、事件时间和已读事实，不含车型、正文、车主/处理人身份、档案或私有链接。事件事实和当前会话状态分别显示。
4. 实现和文档同步维护严格 API/OpenAPI、页面切号/隐藏/权限失效清理。已读未知结果可从服务器实际 read_at 复核，不因重试改变已读时间或重复审计。
5. 真实数据库事务回滚、源唯一/多消费者/失败恢复、分配变更/撤权/管理正文隔离、HTTP边界与前端协议/迟到响应，微信/H5及迁移重放验收。

完成诊断消息后，核对整 R7 恢复与需求销项，运行统一门禁，之后再统一上传所有代码、迁移、测试和文档。不自动合并或发布，正式渠道和真机仍R9。
