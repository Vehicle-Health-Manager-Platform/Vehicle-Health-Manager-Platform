> 版本：v1.2｜更新日期：2026-10-02｜状态：按用户提供的原始交付文档 v1.0 恢复终端与认证要求

## 1. 产品目标与边界

### 1.1 目标

交付可上线运营的汽车健康管理 MVP：车主录入车辆与档案、发起 AI 问诊、获得方案与商家报价、预约下单；商家接车检查并交由技师施工；车主核销、评价后，车辆档案自动更新并生成同款车友经验卡片。AI 准确率不是 MVP 量化目标，业务流程闭环是目标。[来源：§1.1–1.2、§2.3]

### 1.2 用户与终端

| 角色 | 终端 | 主要能力 | 来源 |
| --- | --- | --- | --- |
| 车主 | 微信小程序为主，H5 兜底 | 车辆档案、AI、服务、订单、福利、社区 | §1.3–1.4、§6.2 |
| 商家店长/前台 | 微信小程序 | 入驻、选品报价、订单、接车、派工、券、考核 | §1.3–1.4、§6.2 |
| 技师 | 微信小程序 | 接单、拍照报工、方案与配件、质检签字 | §1.3–1.4、§6.2 |
| 平台运营 | PC 网页后台 | 商家审核、标准项目、车型、券池、内容、价格、考核与看板 | §1.3–1.4 |

### 1.3 范围与优先级

- F01–F10、F13–F14、F16–F18、F20 为 P0；F11–F12、F15、F19 为 P1。详细功能见第 2 节。[§2.1]
- 车主端固定五个 Tab：首页、服务、AI、档案、我的；车友圈从“我的”等入口进入，没有独立 Tab。[§1.4–1.5、§3.2]
- 商业规则：平台内成交订单按 3% 向商家抽佣；新入驻商家前 3 个月免佣；券核销不抽佣，券成本由出券商家承担；无入驻加盟费及统一装修/品牌要求。区域独家、推荐位和高级数据看板只预留字段及入口。[§1.6]
- 排除：独立社区 Tab、内容发布编辑器、评论点赞、KOC 培养、商城实物交易、抽奖、实时人工客服、自驾游/社交动态、直播、多语言、海外部署及平台自营修车/售货。[§1.5]

### 2.1 三条端到端流程

1. **车主用车**：注册登录 → 录车 → 查看提醒/档案/AI → 获得方案与商家 → 比价预约 → 商家接车检查 → 车主确认 → 派工 → 技师施工报工 → 质检 → 到店验码 → 评价 → 档案更新 → 车友经验卡片生成。[§2.3]
2. **商家入驻**：资质提交 → 运营审核 → 区域名额判定 → 审核通过 → 建店员推广码 → 选品定价 → 上架 → 引导到店客户扫码注册。[§2.3]
3. **接车检查**：扫码进入订单 → 前/后/左/右/车顶拍照 → 仪表盘里程 OCR/档案比对 → 油量与内饰拍照 → 标注已有损伤 → 生成接车单 → 通知车主 → 确认或异议 → 归档。[§2.3、§5.8]

### 2.2 订单状态与阻断

来源文档 `order.status` 定义：`0待付、1已付待接车、2已接车、3施工中、4待核销、5已完成、6已取消、7争议`。[§7.2] 实现须围绕第 2.1 节流程校验状态转换，不允许前端直接设置状态。接车未完成且车主未确认时禁止派工；车主异议时标记争议并阻断施工；未上传施工防护照时禁止报工；商家下架项目后既有订单仍使用下单快照。[§2.4、§5.8–5.9]

### 2.3 异常处理

| 场景 | 要求 | 来源 |
| --- | --- | --- |
| 断网 | 显示网络连接失败与重试，保留未提交表单 | §2.4 |
| 接口超过 8 秒 | 自动重试一次，仍失败提示重试 | §2.4 |
| token 失效 | 静默刷新，失败后登录并回跳 | §2.4 |
| 定位失败 | 按城市中心排序并允许手选区域 | §2.4 |
| OCR 失败 | 识别结果可人工修正，不阻断流程 | §2.4 |
| 区域商家满额 | 告知名额已满，可换品类 | §2.4 |
| 券领完/过期 | 按钮置灰，点击给轻提示 | §2.4 |
| 被邀请人已注册 | 不计数，并给轻提示 | §2.4 |
| 用户无档案问 AI | 通用回答并提示录入档案 | §2.4 |
| 接车单异议 | 状态置争议，阻断派工，通知商家 | §2.4 |
| 第三方 AI/OCR 不可用 | 通用知识回答或手动输入，不阻断主流程 | §13.11 |

## 4. 系统、权限与数据规格

### 4.1 技术组成

| 层 | 交付文档指定方案 | 来源 |
| --- | --- | --- |
| 车主/商家/技师前端 | uni-app 3（Vue3），编译微信小程序；车主另编译 H5 兜底 | §6.1–6.2 |
| 运营前端 | Vue3、Vite、Element Plus | §6.1 |
| 后端 | Java 17、Spring Boot 3.x、Spring Cloud 网关/鉴权；模块化单体先行 | §6.1、§6.5 |
| 数据与异步 | MySQL 8.0 主写从读、Redis 7、RabbitMQ、MinIO、Milvus | §6.1、§6.6 |
| AI 与 OCR | DeepSeek 或通义千问 API、LangChain4j、RAG、PaddleOCR 服务 | §6.1 |
| 代理与部署 | Nginx、Docker Compose；Gitea+Drone 为原文档假设，也允许 GitHub Actions | §6.1、§10 |

后端按 `gateway/common/user/vehicle/merchant/order/coupon/point/service/ai/check/community/admin/job` 分包，单体部署、保留拆分边界。RabbitMQ 用于档案更新、社区卡片和通知；车主小程序进度使用轮询与订阅消息兜底，运营/商家 PC 与技师可使用 WebSocket。[§6.1、§6.5]

### 4.2 身份验证与授权

- 车主：微信 code 换 openid，关联手机号，access token 2 小时、refresh token 30 天；商家：账号密码加短信验证码，并校验商家状态；技师：微信授权登录后首次绑定商家工号；运营：账号密码加二次校验。[§2.1、§3.1、§6.3]
- 请求携带 `Authorization: Bearer <token>`；网关进行 RBAC、限流和日志。服务端每次再校验 `user_id`、`merchant_id` 或派工归属，不信任前端资源 ID。[§2.2、§6.3–6.4]
- 车主只读写本人档案和订单；商家只读写本店订单与数据；技师只读写本人工单；运营按后台权限管理全局资源。未明确授权即拒绝，越权返回 `40300`。[§2.2、§8.2、§13.6]

### 4.3 数据模型与约束

- 表与字段使用小写蛇形；原文要求 MySQL InnoDB、`utf8mb4`、`BIGINT UNSIGNED` 主键、`DATETIME` 时间、`DECIMAL(10,2)` 金额、`JSON` 扩展字段，以及逻辑删除和归属索引。无物理外键，应用层校验关系。[§7.1、§7.3]
- 第 7.2 节给出可见 `CREATE TABLE` 的 16 张表：`user`、`brand`、`series`、`model`、`maintenance_rule`、`vehicle`、`vehicle_archive`、`merchant`、`standard_project`、`merchant_project`、`package`、`order`、`pickup_check`、`repair_protection`、`technician_report`、`delivery_compare`。以上表的字段和索引以来源 SQL 为准。[§7.2]
- 第 7.2 节另点名但没有给出建表语句的实体：`coupon`、`user_coupon`、`assessment`、`invite_record`、`community_content`、`community_interaction`、`point_flow`、`point_exchange`、`circle_follow`、`ai_plan_rule`。其结构需要在 `docs/sql/init.sql` 中形成可执行版本，不能把来源中的“见第 5 章”当作已给出 SQL。[§7.2]
- 订单需保留商家项目下架后的历史快照；写接口以 `idempotency_key` 24 小时去重；异步档案与社区更新也须避免重复记录。[§2.4、§8.5]

### 4.4 API 契约

- 所有接口返回 `{ "code": 0, "message": "success", "data": {}, "request_id": "..." }`；失败 `code≠0`。分页返回 `list/page/page_size/total`，默认每页 20、最大 100；排序支持 `distance/rating/price` 和 `asc/desc`；时间筛选为 ISO8601。[§8.1、§8.5]
- 已列错误码：`40100` 未登录/失效、`40300` 无权、`40400` 不存在、`42900` 限流、`50000` 内部错误、`40001` 参数错误、`41001` 商家满额、`42001` 券领完/过期、`42002` 邀请上限、`43001` 接车未完成、`43002` 防护照片未上传。[§8.2]
- 第 8.3 节列明的核心 API 路径与角色须保持兼容，覆盖认证、车辆/车型、档案、驾驶舱、AI、服务/商家、订单、券/邀请/积分、社区、接车/报工、运营。第 8.4 节中的车辆添加、AI 对话、商家列表、订单创建、接车提交示例是字段基线。未列出的页面所需接口仍须纳入正式 OpenAPI 文档。[§8.3–8.4]
- 全部写接口包含由前端生成的 UUID `idempotency_key`；服务端 24 小时内去重。[§8.5]

### 4.5 安全要求

HTTPS、HSTS、CSP；密码 bcrypt；密钥只从环境变量读取；SQL 参数化，富文本白名单过滤；用户 60 次/分钟、IP 300 次/分钟，短信 60 秒一次且每日不超过 5 次；上传只接受 jpg/png/jpeg/webp，单文件不超过 10 MB（原文标为假设），病毒扫描、私有存储桶及签名 URL；审核、退款、上下线、改价记录审计日志；手机号、车牌、VIN 对外脱敏。[§6.4]

### 5.2 测试与上线门禁

- 单元测试覆盖券发放、邀请计数、考核计算、里程比对等核心业务方法，覆盖率至少 70%；接口测试覆盖全部接口的正常、边界、异常和越权；端到端测试覆盖 §2.3 三条主流程；权限矩阵逐格验证。[§9.1]
- 微信小程序在微信开发者工具及 iOS、Android 真机验证，宽度 `375/390/414`；车主 H5 兜底覆盖 `320–1920`；运营 PC 后台验证 Chrome/Edge/Safari 及 `1200/992/768` 断点。[§9.1–9.2]
- 核心读接口 P95<300ms、P99<800ms；写接口 P95<500ms；首页、商家列表和订单创建各 500 并发，错误率<0.1%；超过 200ms 的慢查询应优化。[§9.3]
- 验证跨用户/商家越权、SQL 注入、非法/超大/可执行文件上传、限流及响应脱敏；安全扫描无高危。[§9.4–9.5]
- 上线时 P0=0、P1=0，P2≤5 且有修复计划；核心接口自动化用例 100% 通过，性能指标达标。[§9.5]

### 5.3 部署与运维

应用与数据库两台服务器起步（4C8G、4C16G；Ubuntu 22.04 是来源假设）；Docker≥24、Compose≥2.20；域名及 HTTPS。Compose 包含 mysql、redis、rabbitmq、minio、milvus、backend、nginx。使用版本 tag 部署，初始化 `docs/sql/init.sql`，构建后端、车主 H5 和运营后台，并按原文构建和审核三端小程序；健康检查 `/actuator/health` 为 UP 后人工跑主流程。后端镜像、小程序版本及 H5/运营静态资源按原文回滚，数据库迁移需可逆或灰度。JSON 日志、Actuator/Prometheus/Grafana 告警与注册/订单/券/AI 业务指标按 §10.6 实施。[§10]
